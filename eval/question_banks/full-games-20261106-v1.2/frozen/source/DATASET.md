# Jity 固定完整游戏录制数据集

此目录保存 2026-11-06 经用户授权的真实 API 录制。完整录制会话表示游戏按自身规则产生结束状态及结局，不等于所有主线章节或配置结局均已通关；若由游戏原有预算收束逻辑结束，最终覆盖说明会明确注明。最终完成状态以 `summary.json` 与 `report.html` 为准；只有合法 `game_over`、实际结局、全调用严格离线重放与重载均通过的正式局才计为完整。`smoke/` 是采集前的小规模验收，不计入四局。

## 最终结果

四局均由 Jity 原有的 50 次有效推进预算合法收束，实际路线同为 `budget-incomplete`，结局同为“未竟的追寻”。这是四份完整结束的录制会话，调查本身未完成，不是四种不同配置结局，更不代表主线全部通关。全量验收已从原始响应严格重放 486 次实际 HTTP 尝试，网络尝试为 0；关键状态、结局与重载均通过。

## 可重复运行

```sh
/Users/davidz/Documents/GitHub/jity-eval/runs/full-games-20261106/replay.sh
# 只重放一局
/Users/davidz/Documents/GitHub/jity-eval/runs/full-games-20261106/replay.sh --game game-01
```

固定核心文件的哈希核验入口为 `/opt/anaconda3/envs/jity-backend/bin/python attachments/verify_seal.py`（在本数据集目录内执行，或使用该脚本绝对路径）。`seal.json` 固定原始调用、检查点、消息时钟、冻结源、审批、附件及交付验证证据，并包含已有重放的结果/差异证据；可再生成的汇总、单局汇总、报告、重放/恢复数据库缓存以及后续新增的重放文件不属于这一固定范围。哈希核验不替代逐调用严格重放。

脚本进入数据集目录并使用冻结的 jity-eval、Jity 源码及 `attachments/recovery-version-v2.json` 指定的恢复适配器；较早的恢复版本也保留以追溯修复过程。需 Python 3.11 及 `manifest.json` 记录的后端依赖，脚本当前指向本机已有的 `jity-backend` Python。`capture replay` 不读取 `.env`、不继承模型密钥、没有上游网络 transport，并通过进程审计拒绝 socket/DNS/子进程调用。这里的“断网”是该进程禁止网络，不是关闭整台电脑的网络。

重放从初始状态经过真实 Jity `ScenarioGenerator.generate`、Director/Narrator、解析/修复、SCORE 校验、战役推进、记忆与摘要、数据库提交，从原始 HTTP 响应精确恢复。每步检查完整 state、output、memory、progress、时间线头与确定性内部版本 ID。仅数据库创建/更新时间等非游戏字段不参与等值比较。

检查点是核对证据，不会注入到运行中替代模型响应；缺失、错序、不匹配、未消费、未完成或被更改的响应均为错误。原 API 的错误、重试和嵌入不可用后的现有 hash 回退也会重演。重放不是重新请求模型，不要求真实模型重采样逐字一致。

## 内容

- `manifest.json`：预算授权、实际请求模型/解码配置、依赖版本、源代码/提示词/知识库/战役/tokenizer 哈希。
- `sources/`：不含 `.env` 的 Jity 与评测器冻结源码及本地 tokenizer。
- `budget.sqlite3`：五个流程共享的预留、实际报告用量及停止账本。
- `game-01` 至 `game-04`：任务推进、探索互动、物品变化、分支/风险策略，种子 7301–7304；随机骰点独立于策略，不为制造失败或结局挑选骰点。
- 每局 `calls.sqlite3`：按实际 HTTP 尝试序号写入的请求、原始响应、用量、错误，以及解析/校验/检索/记忆等事件。`calls.json` 为原始调用可读导出，请求另存解析 JSON；请求与响应原始字节保留 Base64，应用解析结果见事件与 traces。
- `intents/`：生成前持久化的玩家行动、选项、随机骰点、选择理由、父状态指纹。
- `checkpoints/`、`traces/`：提交后状态及每步完整审计。
- `initial.sqlite3`、`runtime.sqlite3`：仅供核验和后续检查点探针准备的独立数据库。
- `executions/`：中断恢复时从头构建的独立临时运行；不会把同一行动重复提交到正常存档。
- `replays/`：各次严格重放的新数据库、逐步差异（如有）和验收结果。
- `attachments/render_report_v2.py` 与 `render_report_v2.sha256.json`：交付版纯展示渲染器及独立哈希。它仅从汇总 JSON 生成 HTML，不执行游戏；原冻结执行源码、原报告渲染器和原始调用保持原样。`replay.sh` 与 `resume.sh` 末尾使用此版本更新报告。

## 费用与限制

已批准总上限 US$10，850 次实际请求，输入 1200 万、输出 300 万 tokens；每个 SDK 请求最多自动重试两次，初始正式局提交行动上限为 50，小验收最多 8 次行动。由于本地审查拒绝的行动会生成时间线节点、但不计入战役推进，用户随后明确批准四局提交行动上限提高至 80；Jity 自身的战役预算仍为 50 次有效推进。原 manifest 保持不变，修订凭据见 `approvals/action-limit-80.json` 和哈希旁文件，续采工具版本单独留档。发请求前按 UTF-8 字节保守输入界限与 `max_tokens` 预留；未知用量保留预留，超出预留后持久停止。按 [DeepSeek 官方价格页](https://api-docs.deepseek.com/quick_start/pricing/)（2026-11-06 核对），峰时非缓存输入 US$0.30/M、输出 US$1.20/M 用于保守估计，不把估计称为账单实际费用。嵌入探测没有可核实单价，单独标为未知，受 15 次未定价及 850 次总请求上限约束。

采集使用 `deepseek-flash`、关闭思考；API 返回的模型标识另存，不声称供应商别名是可永久锁定的模型快照。温度、输出上限、响应格式等逐调用保存。未生成背景图、未加入付费玩家模型、未执行三组真实模型探针。

四局仅为固定回归与后续检查点探针的历史材料。原录制答案不是三组记忆消融对照的新答案；不同策略不保证覆盖特定物品消耗、失败或结局。实际观察到的覆盖和未覆盖目标均列在报告；此数据集不证明长期记忆能力。

## 如何理解结束状态与覆盖

报告中的“已提交行动”是持久化到时间线的行动次数；“战役有效推进”来自最终检查点 `progress.turns_total`。本地审查拒绝等行动可能已形成时间线记录，却不推动战役，因此两者不要求相等。应用级解析失败在成功提交前的重试也不增加已提交行动数。采集器的 80 次行动停止上限与 Jity 自身的 50 次有效推进预算是两种不同限制：前者在尚无结局时停止必须记为未完成；后者若经过原有结局规则产生 `game_over`，记录为真实预算收束结局，并明确其未完成调查的含义。

每局的 `completion_context` 汇总有效推进数、章节位置及结束依据；章节和小节索引均从 0 开始。`未竟的追寻` 对应这次记录中实际采用的 `budget-incomplete` 收束，不能解释为所有主线完成或某个未触发的配置结局成功。具体结局仍须结合原始调用、最终检查点和严格重放证据核对；报告不只根据结局名称推断路线。

覆盖计数按已记录事件条数展示，同一物品或人物可多次出现，不代表唯一实体数量。物品获取、移除、遗失和损毁与明确的 `consumed` 消耗状态分别核验，不能把移除直接当作消耗。不同剧情、章节、锚点与失败检定是可观察事件；探索、物品或风险策略只是选项选择方法，不证明某条配置分支已经通关。四局均未观察到明确消耗状态，也尚未覆盖多个不同配置结局；各局的 `coverage.uncovered` 均保留 `consumed_item_state`。

## 已知解析失败与版本化恢复

第三局发生两次真实的剧情解析失败：第 23 次行动的 Narrator 返回有效 JSON，但 `option_checks[3].requires_check=null` 不符合布尔 schema；第 24 次行动的 `option_checks[2].difficulty=""` 不符合允许的难度枚举。两次随后请求的模型修复响应都缺少最外层结尾花括号。四个原始响应均保留在正式调用序列中，两次失败都未提交行动；后台维护只更新内部记忆版本标识。

第四局第 51 次行动又发生两次结局正文校验失败，原因是超过 180–260 字要求，而不是 JSON 解析错误。第一个应用尝试的两次结局改写（HTTP 序号 113、114）为 353、286 个非空白字符；第二个应用尝试的两次改写（117、118）经既有标点归一化后均为 288 字，仍不合规。四次 `ending_narrative` 原始响应均保留，前两次应用尝试没有提交行动。两次重试沿用同一选项索引 2 和骰点 3；第三个应用尝试的 Narrator（序号 120）返回合规的 250 字结局且无独立对话，直接采用，不再额外请求结局改写。

恢复适配器在确认实质状态、时间线头与战役进度未变后，以同一持久化行动和骰点重试最多 2 次。第三局第 23、24 次行动实际各发生 1 次应用级解析重试，第四局第 51 次行动发生 2 次，合计 4 次；所有 SDK 自动重试均为 0，两者分别计数。它不会修写坏响应、重置状态或用快照代替响应；记录与离线重放均经过原始失败过程。相同实际请求合并 SDK 和应用层最多 3 次 HTTP 尝试。原停止阶段的调用与状态快照另存于 `validation/before-recovery/`，恢复适配器、驱动及哈希清单位于 `attachments/`。

另有原 Jity 的 PCB 人物记忆提取提示词格式化错误：在发起模型调用前报错，真实 PCB API 次数为 0。这一未覆盖分支和重复维护警告将保留；NSB 摘要独立正常工作。未修改该既有游戏逻辑。

嵌入端点返回的 HTTP 404 原始响应也完整保留；Jity 随后使用原有的 SHA-256 本地回退。严格重放复现这些错误和回退，不将其标记为远程语义嵌入成功。PCB 与其他运行警告可能在中断恢复重演已有前缀时再次记录；报告的警告条数不是独立失败次数，更不是额外付费请求数。真实请求按 `calls.sqlite3` 的 HTTP 序号计数，异常分组仅改善显示，完整原始记录仍可展开。

## 消息时钟输入

第二局第一次结局重放发现原提示词包含最近消息的 SQLite `created_at`，而重建数据库自然产生了新时间。原请求与响应均未修改。`message-clocks.json` 保存每条消息的身份、正文哈希和真实时间；已有记录从原数据库提取，并对实际结局请求中的消息逐条核对。原数据库另存于 `validation/message-clock-origin/`，其哈希与时钟证据关联。后续真实提交会先持久化新消息时间，再允许下次调用使用它。

离线重放仅恢复 `session_messages.created_at` 这一外生输入，不删掉提示词字段、不放宽 HTTP 指纹匹配，也不注入剧情答案或状态。记录版本及恢复附件版本分别保留在 `manifest.json` 和 `attachments/recovery-version*.json`。当前 Jity 工作区另已按用户建议把未来结局素材收窄至 `role`/`content`；本数据集仍使用原冻结游戏版本。

最终数据库的历史节点可能在后续后台维护时更新内部记忆 `version`。逐回合严格重放仍核对完整检查点和内部版本；独立事后审核只有在同节点的完整维护事件证明实质状态相同、仅内部版本变化时才接受，并逐项列出证据，不隐藏物品、剧情或记忆内容差异。
