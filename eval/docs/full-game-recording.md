# 真实 API 完整游戏录制与离线重放

这套工具录制实际游戏发生的外部请求和原始响应，并用相同输入在离线环境重新执行游戏流程。它用于形成固定回归数据和后续检查点探针的历史来源。录制的 4 局原始答案不是 `full` / `recent` / `state` 三组探针的新答案；重放成功不证明长期记忆能力，也不要求重新调用模型时逐字生成相同内容。

## 执行顺序与费用

1. 检查两个工作区的当前实现及未提交改动，运行相关离线回归。
2. 确认实际模型、解码参数和计费方式，取得用户对总费用上限的确认。
3. 先录制小规模真实流程，包含实际摘要调用；若主流程未触发，另行保留明确标识的摘要冒烟记录。
4. 断网严格重放小规模记录，通过后才正式采集。
5. 使用独立数据库、会话、输出目录，分别采集 4 种可复现策略；每局结束后严格重放并核对重载。

总费用限制覆盖验收片段、4 局及重试，不仅覆盖成功响应。每个实际请求发送前预留费用或用量；用量未知或请求完成状态未知时保留预留，不把未知记为零。另设每局回合上限、每请求重试上限及全局请求/token 上限。预算耗尽时停止；未达到真实游戏结束的局仍标记为未完成。

当前模型和费率以本次 `manifest.json` 为准，不应从 README 的默认值推断。模型名称可能是可变别名，因此同时保留请求模型和响应中的实际模型标识。费用估算和服务商提供的已知费用分开记录；最终账单以服务商为准。不得保存或打印 API Key，报告不得包含认证请求头。

## 证据与严格回放

录制覆盖所有实际发生的外部调用，包括 Narrator、Director、开场选项、审查（若实际调用模型）、摘要、人物记忆、章节回顾、结局、JSON 修复以及嵌入探测和嵌入请求。当前纯本地审查不应计为模型调用；发生的嵌入探测失败也必须保存。

每次实际 HTTP 尝试保留调用顺序、局次、回合、时间线节点、用途、请求内容、模型和解码参数、输入指纹、原始响应、完成标记、失败/超时/重试和可获得的用量。上层解析结果、校验前后输出、最终采用响应、检索结果、记忆写入、玩家行动和骰点与回合检查点关联。后台记忆工作完成后再生成稳定快照。

严格回放必须匹配实际调用顺序和请求指纹，提供原始录制响应给原游戏解析/校验代码；不使用最终剧情 JSON 代替模型原始响应，不用后续检查点掩盖中间缺失。缺失、不匹配、未完成流式响应及未知发送结果明确报错。网络边界应在回放期间拒绝外部连接，不能将未命中记录转为真实请求。

这里的“断网”是独立回放进程中的 Python 审计硬阻断：禁止 socket 连接、DNS 解析和子进程，并且回放 transport 没有真实上游。它不关闭电脑 Wi-Fi，也不是针对恶意原生代码的操作系统隔离。回放从初始状态开始，用原始响应经过真实 `generate` 流程重建完整前缀；初始及中间检查点只用于比较结果，不会被装载为替代缺失响应的捷径。

回放核对所有已录调用是否被消耗、关键状态、实际结局及独立重载结果。与时间、耗时等非确定性元数据有关的规范化必须明确列出；不能把物品、记忆、骰点或剧情差异当成无关字段忽略。

## 恢复与隔离

正常游戏数据库不参与写入。录制日志及时提交并同步落盘；每局保留自己的数据库、会话和检查点。行动意图和随机结果先记录，再提交行动。恢复时识别已提交回合，禁止重复提交；未提交回合复用已保存的骰点和已完成调用。

若相关原始响应均已完整落盘，但行动因已知 `LLMOutputParseError` 而未提交，可对同一持久化行动与骰点重试最多 2 次。这包括 JSON/Pydantic 解析失败及其修复仍失败，也包括结局正文格式或长度校验失败；并不是只允许 JSON 错误，也不是对任意异常都自动重试。重试前核对时间线头、实质状态和战役进度未变；只允许后台维护产生的内部版本标识变化，不回退它。原始失败响应仍参与严格重放，不修写响应或注入后续状态。同一用途、回合与实际请求正文的 HTTP 尝试总数最多 3 次，合并计入 SDK 与应用重试，不能叠加放大。

外部服务和本地数据库之间不存在通用的原子事务。进程若在请求发出后、原始响应持久化前退出，不能声称能自动实现 exactly-once；应保留未知请求、预留费用并停止相关恢复，明确报告该局未完成，避免悄悄重发或虚构响应。

旧版结局请求曾包含数据库消息时间。对此，`message-clocks.json` 保存实际消息时间，并按消息 ID、角色、正文指纹等逐项核对后恢复；请求匹配不会忽略时间字段。新录制在回合返回前同步该日志，因此下一回合使用的时间已落盘。但若进程在数据库提交后、时钟日志落盘前被强制终止，尚未用于后续请求的新消息时间可能丢失，恢复时这些时间来自重建数据库；不能承诺每次临时提交的墙钟值都被保留。已用于原始请求的时间缺失或不一致必须失败，不能自行替换。本次旧数据的时间来源数据库另行归档，并与原始结局请求交叉核对。

## 策略和覆盖边界

四局分别侧重常规任务推进、探索与人物互动、物品获取/消耗及状态变化、不同分支与失败检定。策略使用固定种子和已记录规则，不新增付费玩家模型。通过合法动作推进，不直接修改游戏状态制造结局。

策略目标不是覆盖证明。报告应列出实际出现的物品变化、摘要、人物互动、分支、成功/失败检定和结局；未出现的目标如实保留。当前正式采集默认最多 80 次提交行动，Jity 自身的战役推进预算仍为 50；被本地审查拒绝的行动不消耗该战役预算。达到提交行动或费用限制但没有 `game_over` 和实际结局的记录不能计为完整游戏。小规模验收记录不计入 4 局。

## 浏览器报告格式

`render_capture_report(dataset_dir)` 读取同目录的 `manifest.json` 和 `summary.json`，原子更新自包含 `report.html`。可直接用浏览器打开，不加载外部脚本、字体、图片或网络数据。尚未生成或格式损坏的输入会在报告中显示，不会显示为成功。

`summary.games` 每项主要字段如下；原始额外字段也会展示：

```json
{
  "id": "game-01",
  "kind": "game",
  "strategy": "任务推进",
  "seed": 103,
  "status": "completed",
  "turns": 42,
  "game_over": true,
  "ending": {"id": "实际结局标识", "name": "实际结局名"},
  "calls_by_purpose": {},
  "calls_by_model": {},
  "usage": {"input_tokens": 0, "output_tokens": 0, "unknown_calls": 0},
  "cost": {"known_usd": null, "estimated_usd": null, "reserved_usd": null},
  "retries": 0,
  "coverage": {"observed": [], "uncovered": []},
  "errors": [],
  "replay": {
    "status": "passed",
    "network_attempts": 0,
    "all_calls_consumed": true,
    "key_state_match": true,
    "ending_match": true,
    "reload_match": true,
    "errors": []
  },
  "path": "games/game-01",
  "summary_path": "games/game-01/summary.json",
  "replay_path": "games/game-01/replay.json"
}
```

示例只说明结构，不是已采集数据。真实缺失 token 或费用使用 `null` 或省略，不应填 `0`。正式完成计数要求 `status` 为 `complete` / `completed`、`game_over=true` 且结局非空；严格重放验收还要求上述五项核对证据齐全且无错误。`kind=smoke` / `summary_smoke` / `acceptance` 单列为验收片段。

报告只生成指向当前录制目录内既有文件的相对链接，不接受外部 URL、父目录或越界符号链接。浏览器筛选支持记录类型、完整验收状态和全文搜索。它不修改原始数据，也不从数据库或网络补造缺失证据。

## 命令入口

完整录制命令集中在 `python -m jity_eval capture` 下。在 Jity 仓库的 `eval/` 目录先查看计划；此命令不发起付费请求：

```bash
cd eval  # 从 Jity 仓库根目录开始
/opt/anaconda3/envs/jity-backend/bin/python -m jity_eval capture plan \
  --jity-root ..
```

取得总预算确认后，以一个**尚不存在**的目录启动。下列 `--approval` 内容必须替换为本次真实授权记录，示例本身不构成授权。`--smoke-only` 只完成小规模录制和离线验收；去掉此参数时，工具仍须先通过摘要验收关卡，才自动进入 4 局采集：

```bash
/opt/anaconda3/envs/jity-backend/bin/python -m jity_eval capture record \
  --jity-root .. \
  --output ../../jity-eval-runs/full-game-recording \
  --budget-usd 10 \
  --approval '替换为用户实际确认的预算及限制' \
  --smoke-only
```

恢复继续使用同一目录的冻结输入和同一总预算。恢复前已完成的调用只作离线前缀重建，不重新付费；未知请求结果会停止，不能自动补发。`resume` 也接受 `--smoke-only`：

```bash
/opt/anaconda3/envs/jity-backend/bin/python -m jity_eval capture resume \
  ../../jity-eval-runs/full-game-recording
```

数据集保留本次运行的 Jity 与 jity-eval 源码。长期回归时应使用冻结评测器，避免后续工作区修改混入原录制。先切换到数据集目录，再使用冻结包路径；Python 的当前目录优先于 `PYTHONPATH`，因此不要在另一份 jity-eval 源码根目录执行冻结版本命令：

```bash
cd ../../jity-eval-runs/full-game-recording
env PYTHONPATH="$PWD/sources/evaluator" \
  python -m jity_eval capture replay "$PWD"
```

追加 `--game game-01` 只重放指定局。`replay` 只使用原始录制响应并禁止网络，不需要 API Key。源码、配置、提示词和 tokenizer 资源的冻结散列不一致时应拒绝运行，不应手改 manifest 绕过。

仅重新生成浏览器报告：

```bash
/opt/anaconda3/envs/jity-backend/bin/python -m jity_eval capture report \
  ../../jity-eval-runs/full-game-recording --open
```

运行所需 Python 环境应包含 Jity 后端依赖，离线报告本身只使用标准库。换电脑时应重建 `manifest.json` 中记录的依赖版本；冻结源码不等于冻结了 Python 解释器或全部依赖。

报告回归可单独执行：

```bash
python -m unittest discover -s tests -p 'test_capture_report.py' -v
```
