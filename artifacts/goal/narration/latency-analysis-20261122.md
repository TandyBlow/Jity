# 早交还上界：逐点叙事时间分析（2026-11-22）

## 方法

- 数据：run27–run34（笔记本档，base 1.7B 及各评估臂）与 run35（移动模拟档：单 0.6B + 4× CPU + Intel 核显）的语义证据。
- 字段：`turns[].product.pointNarration` 的 `startedAtMs` / `completedAtMs`，以及 `turns[].timings.waitMs`（整轮等待）。
- 假设：玩家在回合计划里永远排第一（`session.ts` 的 order 数组），所以第一点的叙事完成时间就是「玩家点交还」的最早上界；不含交还 UI 开销，也不含其余点后台结算的尾部。

## 尾部构成（同一批 run27–run34）

第一点之后的尾部不是一个整块，而是 2–5 个后续点：

- 每个后续点先有一段结算空档（1.5–44.6 秒），再写 3–13 秒正文；空档是下一点的语义结算，正文只是零头。
- 最后一笔到整轮结束的差（继续判断 + 收尾）只有约 1–2 秒（例：run27 s05 最后一点 135.8 s，整轮 137.6 s）。
- 因此「早交还 + 后台结算」的后台主体是这些后续点的语义流水线，不是叙事调用；把尾部后台化等于把 2–5 个点的组冻结与六阶段挪到玩家阅读期间。

这意味着 60 秒口径能否成立，取决于玩家阅读首段的时间能否覆盖后续 2–5 个点的结算空档（合计 40.9–156.1 秒）。原型需要测的就是这个重叠率，而不是再换模型。

## 结论

1. 笔记本档：早交还的上界 18.7–50.8 秒，满足 60 秒口径有希望；真正的工作在尾部（40.9–156.1 秒）如何后台化并与玩家阅读时间重叠。
2. 移动档：s05 第一点 150.2 秒，早交还不足以达标；移动档还需要减少每点调用或更换更快的路径。
3. 这些是上界，不是原型结果。交还后的下一次提交仍要等后台尾部结算完成；尾部与阅读时间的重叠程度必须用原型实测。
