# 世界引擎两人开发分工

## 一、拆分结论

两个人按服务边界分工，各自完成一条开发线：

| 开发线 | 负责内容 | 最终交付 |
|---|---|---|
| A：Python 内核与事务服务 | 协议、状态计算、控制状态校验、SQLite、API、恢复与回放 | 不接真实模型也能用固定候选完整运行的世界服务 |
| B：浏览器流程与模型应用 | 浏览器控制器、API 客户端、模型任务与提示词、推理运行层、实验页面与交互 | 能连接固定响应或真实世界服务，完成玩家输入到叙事展示的浏览器应用 |

两条线通过 `/worlds` 协议对接。A 提供权威状态、冻结顺序、工作进度及操作校验；B 根据服务返回的状态安排模型调用、提交候选和展示结果。Python 仍是 apply、preview、合并、回放及摘要的唯一权威。

阶段 0–6 都按上述服务边界分工，双方在接口基线固定后并行推进。A 的一致性与恢复工作较重，B 的模型质量、设备适配和交互工作较重，实际工作量须结合两人的熟悉程度安排。A/B 是职责标记，由两人按熟悉领域认领。

## 二、开工前固定的共同接口

先交付一份最小可用的 v2 接口基线，然后以该提交为共同起点建立两条开发分支。A 维护契约源和导出产物，B 从浏览器调用需求核对字段与示例。接口基线固定不等于阶段 0 已完成；SQL 约束、故障规格及其检查仍按原计划交付。

本批执行入口为 [A0＋B0 共同接口基线实施计划](world-protocol/v2/interface-baseline-plan.md)。v1 基线为 26011c8，原候选为 07924f3；**修订后的 S1 已经 B 正式验收，IF-05 已放行**。11 决定、32 操作及接管流程核对通过，B01 关闭，JS 60/0、Python 300 项、前端 62 项与字节检查均通过，见 [最终验收记录](world-protocol/v2/change-list.md#b-最终复核与-s1-正式验收2026-10-22通过)。验收记录与修订纳入 `feat(world): accept S1 v2 contracts after B review` 提交，本轮不推送；随后 A 推进 IF-03/04a，B 推进 IF-05。S1 验收不代表 IF-05 已交付、完整基线已冻结或 A3 事务已验证。

| 必须固定的内容 | A 交付 | B 核对 |
|---|---|---|
| 数据形状 | Python 定义、v2 JSON Schema；初始世界、PointWork、组清单、候选、检查点、claim、gate | TS 能完整读取、保留并提交，未知字段及版本处理明确 |
| API 请求与响应 | 各端点及 checkpoint 窄操作的请求/成功响应/错误响应示例 | 一次操作需要哪些输入、返回哪些当前状态，不靠客户端猜测 |
| 绑定与重试 | point/head/version/revision、requestId、lease/epoch、claim/generation 的适用范围；同请求不同内容拒绝规则 | 超时后沿用原 requestId；重试与创建新业务操作有明确区别 |
| 调度与门槛 | phase、working 游标、frontier、时间锁、gate/blockedReasons、canCompute 及错误后的恢复动作 | 暂停/恢复成功不等于可以计算；服务返回的新进度可直接恢复浏览器流程 |
| 模型输出与持久化候选的边界 | 每类可提交候选及覆盖清单的 schema、ID 引用与预分配规则 | 提示词输出如何转换为候选；模型不能生成持久化 ID、骰点或阈值 |
| 共同场景 | 手写学校世界、固定模型输出、含动态绑定规则的请求/响应轨迹、预期状态和摘要 | 按固定值、响应捕获/引用和语义断言执行同一轨迹，支持固定响应客户端和真实服务 |

共同场景至少覆盖：A/B 同点暂存、C/D 共同结算和 E/F 续段；空点时间扫描；自动 round 与输入消费；暂停/恢复；响应丢失重发；租约交接与原文副本接续。每条轨迹标出操作、请求绑定、响应、下一 phase/工作进度及允许的下一动作。

### 2.1 共同轨迹的动态字段

A 在 A0 定义并维护轨迹格式/schema、字段匹配分类、摘要预期生成方式及正反例，B 在 B0 实现读取、捕获/引用、请求核对及断言执行。轨迹携带自己的格式版本、适用契约版本/摘要和场景身份；每步声明请求模板、响应捕获路径、响应断言及允许的下一动作，不对整个真实响应逐字比较。

| 匹配方式 | 适用字段与执行规则 |
|---|---|
| 固定值 | 操作类型、枚举、手写模型输出、覆盖清单、预期错误码、确定的时间增量等，按 schema 规范后的值比较；集合及有序数组沿用协议各自的比较规则 |
| 响应捕获与引用 | 服务生成的 world/point/round/group/roll 等 ID、lease/claim token、实际 version/revision/epoch/generation 等，按声明路径保存为命名变量；后续 URL、请求和预期投影引用该变量，不硬编码静态 JSON 中的值 |
| 语义断言 | 校验字段类型、范围、跨步身份一致性、精确的版本/代次变化、token 换新或保持不变、围栏拒绝及 phase/工作进度等；expiresAt 依据服务端测试时钟或请求前后时间界限和约定容差断言，不与客户端时钟直接判等 |

捕获本身不算行为验收。例如交接后的 epoch 即使能捕获，也必须断言它相对旧值按协议递增；同请求重放必须返回原身份。变量未声明、引用未捕获、重复覆盖旧变量、缺失响应字段或缺少必须的断言均失败；新认领使用新变量名，保留旧值用于迟到请求与围栏测试。固定响应模式也执行同一捕获和断言规则，只是捕获到的是预设值。

worldId、实体/任务/change/point 等身份只要进入状态投影或候选投影，就必须同步实例化预期投影中的所有引用，包含描述变化的来源身份；不得替换 ID 后继续比较原静态哈希。固定身份的 golden 场景仍锁定规范字节和固定哈希。动态 HTTP 场景使用独立手写的 expectedProjection 模板，经捕获值实例化，再由 A 提供的测试侧 Python 规范化工具计算预期摘要；该工具不调用实际 apply，也不以服务返回的实际状态或实际哈希生成预期。B 消费生成的 expectedDigests，不在浏览器实现另一套规范化权威。

服务返回的摘要可以捕获后作为下一请求的绑定值，但不能同时充当独立正确性预期。动态身份匹配、摘要模板实例化及固定向量检查属于共同轨迹验收；生产 API 不为测试开放任意 ID/时钟注入入口。

### 2.2 契约变更的自动门槛

A 维护共同 CI（`.github/workflows/ci.yml` 及根级检查编排），B 提供并维护前端消费/轨迹测试与可重复执行的命令。首份接口基线须同时带上双方的最小消费检查，后续每个契约变更在同步另一条分支前必须通过以下全部检查：

| 检查 | 维护与通过标准 |
|---|---|
| 导出一致性 | A：v2 schema、`api-contract.json`、`trace.schema.json` 等生成物从 Python 源按字节重导出并与提交产物一致；手写夹具/向量/SQL 只按 `manifest.json` 的 artifact 哈希校验，不重写；B 的手写 TS 消费类型由类型检查与运行时校验覆盖；提供只检查或临时目录导出模式，不能靠更新预期文件把检查变绿 |
| 摘要 pin | B：提交由 A 脚本生成的 `contract-digest.json`，只覆盖接口生成物，不含夹具/向量/SQL；CI 在单树内重算摘要并比对，契约漂移即失败 |
| Python 正反例 | A：契约合法/非法输入、绑定、规范向量和适用的存储约束检查；不能只验证导出的 schema 能加载 |
| TS 消费 | B：合法响应完整读取/往返、不合法响应拒绝、枚举/错误码及 blockedReasons/canCompute 的实际处理；类型编译通过不能替代行为断言 |
| 共同轨迹 | A/B：分别通过 Python 侧协议检查和 TS 侧请求/响应消费检查，包含动态字段规则、摘要实例化及错误/重试分支；A2 起还运行可用真实 HTTP 场景，A3 起加入恢复/接管场景 |

当前仓库前端已有 `npm test`（Vitest），现有 CI 的前端步骤仅有 lint/build，尚不满足上述门槛。A0/B0 须把测试命令与共同 CI 接线作为接口基线交付：CI 运行 `npm test`（Vitest 已匹配 `src/**/*.test.ts`，覆盖 world 测试）与 `typecheck:world`；`test:world-*` 只用于本地聚焦，不重复接入 CI。具体脚本、测试选择和运行目录写入双方交付记录。尚未实现的 v2 检查不得用旧 v1 测试、空测试集或静默跳过冒充通过；本节规定的是待实现的门槛。

B 的消费层提交由 A 脚本生成的 `frontend/src/lib/world-engine/contract-digest.json`，CI 在单树内比对摘要与 pin，契约漂移即失败。若契约变更同时依赖两条分支的新代码，由 A 在临时集成 checkout 中组合双方指定提交运行检查，无需提前合并开发分支。记录契约摘要、A/B 提交身份、执行命令和检查结果；只有经过验证的同一组合可同步为新基线。B 的消费代码需要修改时，由 B 提供对应提交并一起验证，不能仅凭口头核对放行。

在接口基线完成前，A 可以继续契约与内核，B 可以先做模型运行层、独立任务样本和页面框架。依赖 v2 数据形状的控制器及客户端以已固定的契约为准，不能拿 v1 夹具当成 v2 成功路径。

B 的调度读取服务端冻结的 order、working 游标/集合和 frontier，组织下一次模型调用；组扩张请求的授权、admission、最终状态和合法 phase 由 A 校验。浏览器不另写 apply、骰点算法或控制状态权威副本。

WorldTransport 的固定响应实现按 §2.1 的轨迹模板、捕获变量及语义断言核对请求，返回预设响应/工作状态，也支持预设超时、冲突和失效场景。它不计算世界变化、不自行生成状态摘要、不实现第二套内核；超出轨迹的操作明确失败。固定响应检查之外，按 §7 的 H1/H2 提前连接真实服务验证。

B 的模型任务输出转换为已固定的候选类型；提示词、任务批处理和模型配置可在 B 的目录内独立调整。涉及新增字段、改变覆盖规则或状态语义时，先更新接口基线，不能单方面扩展请求。`canCompute=false` 时停止状态相关模型调度，叙事重试、暂停/恢复和原文副本接续按协议分别处理。

阶段 6 的优化仍在正确闭环之后开展；模型实验可提前独立探索，但不替代固定候选、内核和事务验收。

## 七、并行开发与最后合并

1. **共同接口基线。** A 交付并记录一个契约提交，B 核对动态轨迹及消费方式，§2.2 的双方检查全部通过后，两条分支从该提交开展接口相关实现。无需等待 A 的 SQLite/API 全部完成，B 即可用固定响应开发；此前可先做互不依赖的任务。
2. **分别完成独立验收。** A 用共同轨迹直接测试真实服务；B 用相同轨迹测试控制器发出的请求、模型调用顺序和页面状态。双方分别维护交付记录，不在各自分支宣称已经完成整链联调。
3. **接口变更及时同步。** 新增操作或不兼容字段必须更新契约版本/摘要及示例，按 §2.2 通过双方自动检查后只同步最小契约及必要消费变更。最终合并前，双方交付记录必须指向同一份契约基线。内部重构不要求同步对方分支。
4. **提前 HTTP 联调。** A2＋B1 完成 H1，A3 且 B 的刷新/接管客户端就绪后完成 H2，按下表记录证据。可直接连接对方指定提交启动的服务，也可在独立集成 checkout 运行，无需提前合并两条开发分支。
5. **建立最终集成分支。** H1/H2 通过后，先合入 A，再合入 B；重新导出并核对协议产物，处理约定过的接入文件。两人各自在所属目录修复问题。由 A 汇总总计划及状态，B 维护浏览器验收记录。
6. **完整固定输出整链与真实模型验收。** 最终合并后，在真实 SQLite 服务上跑完全部共同轨迹，再接真实模型完成原阶段 5 验收。H1/H2 覆盖最小连接与恢复路径，不能代替最后的完整整链验收。

| 检查点 | 时机与责任 | 必须通过 |
|---|---|---|
| H1：普通点 HTTP | A2＋B1；A 提供最小服务及启动配置，B 提供浏览器固定输出流程 | 真实浏览器经 HTTP 完成创建世界/根点固定叙事、启动 round、一个普通点的 begin/discover/extend/close/stage/seal/提交及该点叙事 ready；校验动态绑定、实际序列化、请求/响应字段、API 地址/CORS 和状态摘要。FixtureBaselineStore 可用，不宣称通过崩溃恢复 |
| H2：刷新与接管 HTTP | A3 后，B 的刷新/所有权恢复客户端已就绪；A 提供真实 SQLite 服务，B 运行恢复流程 | 在有未提交冻结工作的状态刷新一次并恢复；再交接一次租约，验证 epoch/claim 失效与重领、原文及已保存候选复制不变、旧持有者迟到写入拒绝、已确认工作不重采样；恢复后能继续提交且无重复消费 |

两次检查均记录 A/B 提交、契约摘要、执行命令/步骤、服务配置、轨迹身份和结果；服务地址与配置通过运行参数对接。使用固定模型输出，不要求下载模型。H2 的 TTL/交接可使用服务端测试时钟驱动，真实 SQLite 围栏与事务路径仍须执行；测试时钟不作为生产公开接口。

建议分支命名为 `world-server`（A）、`world-browser`（B）和 `world-integration`（最终合并）。各自在自己的克隆或独立 worktree 中开发，分别使用本地配置、数据库和运行端口；同一个物理工作目录不能供两条分支同时切换开发。

两边“各自通过”是最后合并的输入，合并验收还必须检查以下场景：

| 场景 | 共同通过标准 | 主要定位责任 |
|---|---|---|
| A/B 暂存和 C/D/E/F 分段 | 浏览器不重跑已确认前缀；真实库只在 point 提交时提升已提交进度；回放摘要一致 | A 查状态/事务，B 查调用顺序 |
| 空点与自动 round | 时间先行并完整扫描；输入不重复消费；空 linked 也等待叙事 | A 查规则/绑定，B 查任务覆盖/调度 |
| 超时、刷新与双标签页接管 | 同 requestId 不重复消费；旧 epoch 无法写入；接管文本及候选保持原值 | A 查围栏/幂等，B 查恢复/重试 |
| pending 时暂停、过期后恢复 | 控制状态可保存，canCompute=false 时不调用计算模型，ready 不自动清暂停 | A 查门槛响应，B 查执行与展示 |
| 时间锁、后继预约和源工作损坏 | 非法修改/错绑拒绝；缺失或损坏明确阻断，浏览器不自动重采样 | A 查绑定/来源，B 查错误分支 |
| 真实模型可玩闭环 | 按原阶段 5 完成至少 20 次玩家输入及自动链，记录质量和实际设备成本 | B 主验收，A 处理服务问题 |

最终交付包含两份独立验收记录、共同契约版本、真实服务固定输出整链结果、真实模型实验结果，以及未解决限制。接口一致、文件无冲突和各自测试通过，都不能代替真实服务的整链验收。
