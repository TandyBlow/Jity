# E59 增量叙事：82% 的事实是重复的，只写增量就能用 16% 的字数覆盖 100% 的事实

**Question.** 现役正文里有多少内容是在重复上一 point 已经写过的事实？如果只叙述“相对上
一次的新变化”，事实覆盖与结果标签会不会掉？

**Setup.** 161 个输入按证据文件内的顺序排列，每个 point 与它前一个 point（通常同回合的
上一个 point）比较。事实从句做精确去重：`fresh = 本 point 有、上一个 point 没有`。
增量臂（`compose_delta.py`）只把 fresh 从句 + 全部结算结果 + 时间行交给 E57 的聚簇
组句；若 fresh 为空则保留一句位置锚点。评价按**整段证据运行累计**（玩家逐回合阅读，
信息只需出现一次）。

**Results.**
- 1,901 个事实从句里只有 **437 个是新出现的（23.0%）**；逐 point 看，**82.2% 的从句
  在上一个 point 已经出现**，150 个有历史的 point 里 135 个重复率 ≥80%，中位 90.9%。
- 增量臂：每 point 101 字（中位 59），每回合 307 字；E57 逐 point 组句每 point 324 字，
  现役 1.7B 每 point 177 字、每回合 535 字。
- **累计覆盖（按证据运行）**：

| 臂 | 事实覆盖 | 结果标签 | 累计字数 |
| --- | --- | --- | --- |
| 现役 1.7B | 0.689（292/424） | 0.043（6/141） | 98,037 |
| 规则 E57（逐 point） | 1.000 | 1.000 | 53,102 |
| **增量 E59** | **1.000** | **1.000** | **16,287** |

- 增量臂回合内 8-gram 重复 0.028（现役 0.306、E57 逐 point 拼接 0.49），最长句 58.5 字。

**Interpretation.**
- 现役 1.7B 用 98,037 字只让玩家看到 68.9% 的事实、4.3% 的结果标签；增量规则用 16,287
  字做到 100%/100%。**叙事的瓶颈不是把句子写出来，而是决定这一回合哪些事实值得写。**
  这个决定在规则层面就能做到（新变化 + 全部结算结果），不需要模型。
- 现役正文每回合约 535 字，其中大部分是重复描述上一回合已经成立的场景（护目镜、背心、
  路线图、诺诺的识别带）。这也解释了它读起来“原地打转”：不是文笔问题，是输入没有告诉
  它“这些上一回合已经说过了”。
- 对微模型的启示：分工应该是 **程序做选择（delta + 结果行）→ 微模型做渲染（把选中的
  片段写成自然句）**。E52 的失败（1.24M 端到端模型句式准确率 0.036）正是因为它同时在
  学选择和渲染；把选择从模型里拿走后，模型只需处理 2.7 条/point 的片段。
- 产品层含义：叙事以 point 为单位生成、以回合为单位展示，四个 point 各写一遍同一场景，
  是回合正文 4 倍冗余的直接原因。修法有两种：按回合只生成一次，或把“本回合已叙述”
  传给后续 point。两者都属于叙事输入投影，不涉及语义侧。

**Caveats.** 精确字符串比较会把改写过的同一事实算成 fresh（真实增量率应低于 23%）；
前一个 point 的正文若没有真正展示给玩家，增量会丢掉信息（需要“已展示”记录而不是
“上一 prompt”）；累计覆盖假设玩家逐回合阅读；只覆盖演习世界 17 个证据文件。

compose-delta-rows.json}`。E59。
