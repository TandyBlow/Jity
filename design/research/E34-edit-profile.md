# E34 词级编辑谱：编辑式解码的动作空间

**Question.** 从"oracle 计划拼接"到人写正文，词级操作的真实构成是什么？
（决定编辑式解码器的动作集与模型形态）

**Setup.** `edit_profile.py`：348 段；源 = 选中从句（去前缀）以「。」拼接；
目标 = 人写正文；按 jieba 词序列做 difflib 对齐，统计 opcode 覆盖词数占比。

**Results.** 49,604 个词位：保留 **11.5%**、替换 **22.6%**、插入 **2.1%**、
**删除 63.8%**。即：目标正文是"选中从句"的大幅删减 + 改写——每个从句里只有
一小段词被采用，其余被删掉；新造词极少（插入仅 2.1%）。

**Design implication.** 编辑解码器的主操作不是"写新句子"，而是
1) **从句内 span 指针**：在选中的从句里指出保留的片段（对应 63.8% 删除）——
   这与 v3 候选指针模型的机制同构：短语候选 = 从句内的 span，`<e>` 指针选片段；
2) **局部替换**（22.6%）：同义改写与词序调整，编辑动作的次要但不可忽略项；
3) **连接词与虚词插入**（2.1% + 前一轮的虚词统计）：几乎零成本。
这同时解释了 E33 的失败：自由逐字生成既不擅长"大量删除"，也不受"只写计划内
内容"约束；把候选限制为事实 span，等于把"不能编造"写进了解码结构。下一步按
此形态实现 v3 式编辑解码（候选 = 短语 span，动作 = 指针/替换/删除/连接）。

**Caveats.** oracle 计划来自人类选择（不是模型选择）；词对齐对长距离换序
计为替换+删除；单世界单风格。

**Artifacts.** `edit_profile.py`、`edit-profile.json`。E34。
