## 2. 必须交付的结论

本专项最终要用设计与实验回答以下问题：

1. 非叙事流程应拆成多少个软件组件？每个组件的职责、输入输出、上下游和合并／拆分理由是什么？
2. 每个组件由确定性程序、判别模型、生成模型还是混合方案承担？为什么需要模型，或为什么不需要？
3. 需要哪些模型、任务头与运行时？哪些职责能共享权重，哪些值得专用模型？
4. 同条件下，拟议组合相对现有通用生成方案，质量与整个流程的成本如何？失败和未验证项是什么？

现有 `C1–C7` 是继承文档的职责编号；`ModelTask` 是当前调用种类。两者都不等于最终组件数、权重数或调用数。不得先固定七个模型，再倒推职责；也不得因一个生成模型能够返回 JSON 就认定所有任务应永久合并。

## 5. 工作范围与执行顺序

### 第一步：先完成非叙事全景

覆盖初始世界生成、普通行动、目标分析／被迫反应、共同结果、六阶段变化、继续推进，以及 time／pointPlan 的辅助提议边界。C0 程序权威作为约束说明，C7 叙事作为交接边界说明，不接管它们的实现。

为每项职责给出至少两种有意义的组织方案，例如通用生成骨干单调用与“判别／选择后生成”的拆分方案。无需机械地为每项创造两个方案；不适合拆分时应解释为什么。比较：语义完整性、输入规模、阶段依赖、错误传播、调用次数、可共享权重、可独立测试程度和运行成本。

交付职责到组件映射及建议数量。区分软件组件、模型骨干、任务头、调用步骤；同一模型可承接多个组件，同一组件也可能需要程序加多个调用。建议在实验前可修改，不能把草案命名当成冻结架构。

### 第二步：逐组件判断是否需要模型

为每个候选组件填写：

| 字段 | 必须说明 |
| --- | --- |
| 职责与依据 | 对应原设计章节与 R 编号；不丢功能 |
| 输入与输出 | 语义上需要什么，当前代码实际提供什么，缺口在哪里 |
| 程序可承担部分 | 引用、身份、覆盖、数值范围、确定性关系及流程控制 |
| 模型可承担部分 | 分类、打分、排序、抽取、引用选择、生成或数值预测 |
| 无模型方案 | 能否完整满足要求；只适合作测试参照时明确标注 |
| 模型必要性 | 哪个语义环节需要学习／生成，能否共享，拆分有什么收益与风险 |
| 合法否定与失败 | 区分经判断后的 skip／空目标／无变化／handback 和未检查、缺资料、超时、截断 |

程序可以处理确定性工作，但不得把 NPC 固定 skip、targets 固定为空、结果脚本化、继续判断固定 handback 等做法计作完整能力。判断依据可以作为实验记录，不默认进入闭合 codec 或服务 wire。

### 第三步：模型候选与运行方案

需要模型的任务先筛少量候选，通常 2–3 个足以进行首轮否决。优先探索几十 M 至几百 M 的中文适用方案；规模是探索偏好，不能以缩减原功能满足参数量目标。现役较大模型可作容量／基线对照，质量不足如实报告。

候选表记录：精确模型标识、revision／文件哈希、架构、全参数量与任务头、中文能力依据、许可、训练／微调／蒸馏需求、可共享骨干、量化、分词器、导出格式、浏览器运行时、加载／取消／迟到输出处理、预期成本与未验证风险。下载体积不当参数量，模型卡能力不当项目成绩。

继承的 MiniRBT、T5、Qwen 路线只是候选参考，可以提出其他方案。新选型时查阅当前官方模型卡、论文和运行时文档，记录来源与核对日期；不必为了沿用 C 的工具而选择不合适的架构。暂不下载全部候选，先形成可执行的短名单。

### 第四步：首批深入验证行动、目标／反应与共同结果

全景完成后，优先深入 C2–C4。此处沿用职责编号，实际内部组件数仍由前述分析决定。

| 职责 | 首批必须覆盖的情况 |
| --- | --- |
| 普通行动 | 主角／NPC；pending／consumed／expired；可执行与不可执行输入；基于任务和个性的自主行动；合法 skip 与输入缺失／取消分开 |
| 目标与反应 | 无目标、未准入、已行动、准入后继续牵连、环、同目标多源；以已冻结威胁生成反应；已行动者不重复反应但保留相关骰点信息 |
| 共同结果 | 封闭全组成员与行动完整、缺成员／骰点、不同骰点判定、相互冲突的行动；检查全组一致性，不把逐人独立成文直接拼成共同结果 |

先用现有生成骨干思路建立真实模型基线，再比较拟议拆分。若首轮显示拆分无收益或输入不足，记录失败并调整，不先大规模训练所有任务头。无需在一个大实验中同时验证所有候选。

C5 六阶段变化与 C6 继续判断必须纳入前期架构和选型表，后续按结果深入；C1 初始生成先设计接口和职责，完整生成／修订流程排后。首批交付不宣称这些后续职责完成。

六阶段方案须保留阶段预览依赖、全人物全任务扫描、任务触发后的全人物个性检查和对应人物理智重算；允许合法无变化。继续判断须分别考虑“很可能发生”和“与主角有关”，预算耗尽不能伪装剧情 handback。上述要求不能因本批暂不实验就从架构中省掉。

### 第五步：依据证据修正组合并交接

更新建议组件数、模型共享图和调用流程；标记保留／合并／拆分／待训练／不适用及原因。对拟接入方案给出输入输出示例、缺失上下文、适配位置、失败处理、取消和恢复要求。接线由相应生产目录负责人承接；本专项可先交纯离线可调用模块，不直接修改 B 的运行层。

## 6. 数据、判据与成本纪律

- 新建隔离开发数据，记录每项 sourceGroup、来源、用途、内容哈希、标注依据及参与过的调参步骤。同一原例及改写按同一组划分，不只对比 ID 或整文件字节。
- 不使用 B 的 hv／nv／ns、历次校准和整链调参样本，也不使用 C 的 N2／N3／N4 开发、训练和封存验收样本作本专项选型／训练。已有对照只能引用归档结论；只复用方法和工具骨架，复用实现时记录提交与依赖。
- 去重来源固定到已提交版本，记录来源清单与摘要；读取中的工作区文件不能进入冻结来源。缺失来源报未核实，不静默当零重合。小样本表面去重不能证明语义独立，人工检查改写与同源情况。
- 先登记指标、标注与复核方法、样本分组、通过门槛和失败处置，再对照候选。小样本用于可行性与否决，不声称泛化；正式留出评测另行登记用途，不消耗 C 的封存集。
- 标签依据来自原设计、明确场景与人工复核；模型答案不能自证正确。拟用教师模型造数据时先说明角色、复核方法和污染风险，不把未经复核的输出直接当真值。
- 同一任务各臂使用同一冻结输入、适用的同一判据和可比解码配置。保存原始输入输出、模型身份、结构错误、语义 fail／待人工 review、重试和回退。单列真实推理与程序／模板参照，不挑成功样本报告。
- 成本记录环境、设备、依赖、冷加载、热推理、序列化／阶段交接、调用次数、峰值内存、切换与重试回退。离线 Python 与浏览器分别报告；没有实测就标未验证，不拼接不同设备的数字作为总耗时。
- 对模型输出无论何种形状，检查引用、覆盖、阶段和采纳身份。未完成不自动变成否定答案；恢复不重新采样已经冻结的行动或骰点。不会为实验另建长期人物知识库或世界事实权威。

从当前基线继续开发，不自动追随 C 的每笔提交反复 rebase。后续确需 C 的修复时记录来源 commit、具体路径和原因，检查双方变更后同步同一提交或最小适用改动，不复制一套公共规范自行冻结。跨分支合并目标和时机由项目协调人统筹，生产落地另行安排。

本专项通过 `origin/world-components-logic` 进行远端交接。阶段交付提交到本分支并推送远端，报告提交链接、证据位置和待审范围；不自动合并至其他分支。提交时限定专项路径；不得收编 B/C 并行产生的文件，也不得删除他人原始证据或清理其工作树。

## 9. 首次启动清单与汇报格式

新实现者首次启动时依次完成：

1. 确认在本工作树和本分支，查看 HEAD、`git status --short` 与本文件；保留已有修改。
2. 按 §4 阅读原设计及继承方案，记录职责与现实输入之间的差异，不先修改 B/C 产品代码。
3. 启动 L1：画完整非叙事流程，列建议组件及程序／模型分工，同时列待实验证实的假设。
4. 启动 L2：为首批任务建立候选短名单和隔离数据／判据协议，再开展模型实验。
5. 每批交付报告分支与 commit、任务范围、变更文件、验证命令和证据位置、失败／未覆盖项、资源需求与下一步。

本次交付仅包含专项分支、工作树及交接文档；没有新增模型选型结论、训练、数据集、浏览器适配或生产接线，也没有修改 B/C 的进行中工作。
