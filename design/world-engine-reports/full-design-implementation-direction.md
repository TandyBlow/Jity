# 按完整原设计推进：开发方向与未完成任务

日期：2026-10-28。状态：用户最新方向要求，优先于历史实验中的收窄安排。

> **任务拆分更新：** 用户随后明确先确定组件结构、模型任务和几十M至几百M候选，并授权新增 `world-components` 分支及 `.local/world-components-worktree`。C先做接口/选型与叙事拆分验证，B现有整链工作继续在其分支推进；涉及C方案的接入先明确组件接口和候选验证，不把组件设计推迟到整链之后。下文P0–P3是B产品整链的顺序，不是要求C等待这些阶段完成。

用户明确要求后续完全朝实现自己的设计发展。本文把该要求落实到开发目标、未完成项与验收口径；不是宣布这些功能已经实现，也不变更既有冻结验收范围。

## 1. 产品目标与职责

原设计依据为 [世界状态工作流](../browser-world-state-workflow.md) 记录的十一部分设计及补充要求。程序负责调度、时间、身份、冻结、骰点、确定性校验、应用、持久化和恢复；浏览器模型负责人物行动判断、被迫反应分析、行动结果、自然语言状态变化候选、继续推进判断与叙事表达。初始世界也须按设计分阶段生成并封存。

明确以下执行原则：

- 完整原设计是最终交付目标。少量固定命令、固定单人规则、脚本结果、固定 handback 和有限模板不能替代原设计中的模型职责。
- 上述简化实现可以作为夹具、分层回归、故障诊断或明确标出的对照臂；通过这些检查不代表相应真实模型能力完成。
- 未实现、尚不达标、仅固定输出通过、仅规则场景通过，都必须保留为未完成项。不得通过改提示词职责、固定输出或缩小场景来关闭原要求。
- 模型产生的是候选；Python 依然是状态应用和持久化权威。模型不得自定永久 ID、骰点或阈值，不得通过叙事修改状态。程序不能宣称确定性结构校验证明了自然语言因果正确。
- 某个模型或配置失败，记录失败、成本和原始输出，再调整任务组织、输入、约束或模型能力；不能据此把产品改成封闭规则模拟器。具体模型数量、大小和推理后端以实验为依据，不预先固定。
- 历史“无 LLM、无 WebGPU”“当前模型不能持有状态变化决定权”等表述，只保留其当时实验的事实背景，不能作为禁止实现本次浏览器模型链的产品方向。用户未要求必须使用 WebGPU；也不因硬件选择删减游戏语义。
- 当前叙事门和模板可继续用于用户已指定的首轮场景；新判分门接线不是前置。最终仍须支持原设计的合法世界变化、选择性描述及自然表达。模板回退是明确记录的降级，不能计为模型表达成功。

## 2. 原要求与现状的逐项对应

以下“已有”以源码和既有记录为依据，不扩大成新的 A/B 组合验收。

| 编号 | 原设计要求 | 现状 | 后续工作与关闭条件 |
| --- | --- | --- | --- |
| R01 | 开局固定地点、物品、人物；运行中仅更新登记实体，允许任务树下增添小任务 | 契约、内核已有约束；页面使用内置世界 | 保持实体边界，真实模型正反例验证引用合法与语义越界；未知实体不能靠改写叙事成为事实 |
| R02 | 地点嵌套、人物/物品容纳与相对位置，自然语言外貌和人物任务/个性/理智 | 状态层已有广泛表示；页面和叙事只覆盖子集 | 补齐模型输入/候选和展示，对嵌套移动、物品、地点外貌、相对位置完成可执行场景 |
| R03 | 初始外貌与个性不改写，后续变化保留历史；位置结构化 | 内核已有，模型整链未完整验证 | 真模型生成合法变化及替代引用，验证原文保留、纯解除等分支，不只验证移动和数值 |
| R04 | 世界事实由 S₀＋Δ 构成，状态/摘要/检查点可重建 | Python 回放与 SQLite 已有验收范围 | 对新真实模型提交继续核对；缓存和模型切换不能改变事实来源 |
| R05 | 同点同实体一份合并增量 | 内核合并已有 | 真实多组与连续阶段验证最终投影一致，不以单组单人代替覆盖 |
| R06 | 非关联新轮按理智排序，关联点沿用冻结顺序 | 通用控制器和服务已有，规则页面固定简单流程 | 真实多人物行动和续轮场景验证逐人判断、重排及关联顺序不变 |
| R07 | 骰点驱动被迫行动准入，先冻结全组行动再统一结算 | 控制器/服务、脚本候选和恢复已有；页面 targets 为空 | 模型分析目标、生成反应与共同结果；覆盖多级反应、未准入、环及已冻结成员，不以脚本文本代替 |
| R08 | 已行动人物不重复行动，后续骰点仍影响攻击者结果 | 机制及固定输出检查已有 | 真实模型组场景验证“无第二次反应但结果读取该骰点”，恢复不重掷或重采样 |
| R09 | 位置→外貌→任务→新增小任务→个性→理智；任务与个性按原设计全人物覆盖 | 通用六阶段/preview 已有，规则页面只有固定效果 | 真模型候选按依赖逐阶段应用；任务扫描覆盖全人物；任务达成后个性扫描全人物，允许合法的不变化；不固定成任务/个性/理智必须成套 |
| R10 | 仅由大概率发生且与主角关联的后续行动触发自动推进 | 通用流程已有，规则页面固定 handback | 真模型读取主角、当前世界及本轮变化，分别验证 continue/handback，多轮不重复消费输入，预算暂停不伪装 handback |
| R11 | 每点只读叙事，允许选择、省略、隐藏秘密和暗示，不虚构已结算事实 | 有提交读取、模板、严格短句门及新判分实验，通用支持未完成 | 补齐合法变化的输入投影与表达；保留 mustExpress / mayMention 区分；逐句复制全事实不是最终表达要求 |
| R12 | 不另维护独立人物知识状态，模型从当前世界判断认知 | 新工作流未要求独立知识库 | 后续模型组件沿用，不为绕过语义任务另建事实权威 |
| R13 | 行动描述仅作本次分析，不建长期行动历史 | 冻结工作与恢复已有相应设计 | 原文只按工作态生命周期保存，调试归档与世界存档分开；不能为叙事补能力偷偷新增事件真值 |
| R14 | 工作职责不等于模型数或调用数 | 已有通用端口、队列、多个实验组合 | 先明确软件输入/输出和职责，依据质量与成本选择一个或多个模型；不预设七模型或固定调用总数 |
| R15 | 按设定分批生成初始实体、描述、任务、个性和理智，确认后封存 | 有创建模板校验和初始任务接口，完整生成/修订流程未交付 | 分阶段生成草稿、程序分配身份和校验、修订后确认封存；手写小世界只作为开发验收输入 |
| R16 | 小世界完整可玩，至少20次输入，覆盖自动链、共同结算、恢复、历史与删叙事缓存重生 | 已有受限页面、恢复验收和叙事实验，不等于完整真实模型通过 | 两个真实场景首轮后扩展；逐任务保留真实调用、错误、重试、回退及端到端等待，满足原阶段5再关闭 |

R01–R14 对应原方案列出的十四条必须保留规则；R15/R16 是开局生成与最终可玩交付要求，单独列出防止遗漏。没有将“机制存在”标成“模型能力完成”。

## 3. 先明确的组件边界

组件接口可以随着实现细化，先保持原职责，不能在组件拆分时转移或删除语义工作。

| 边界 | 必须承接的职责 | 不能用来替代它的现有简化 |
| --- | --- | --- |
| 行动 | 指定人物按最新工作状态、任务、个性和输入消费状态判断 act/skip 与行动文本 | 只解析移动/压力试验/恢复练习，或所有非主角固定 skip |
| 被迫反应 | 分析已确认行动的目标，按服务骰点/资格生成并冻结反应 | targets 永远为空，或预写目标和反应文本 |
| 共同结果 | 根据全组冻结行动及完整骰点判定生成结果候选 | 固定“既定结果”或先由规则确定全部结果再称模型已结算 |
| 六阶段变化 | 在工作态和各阶段依赖下生成覆盖完整的候选，交 Python 验证/应用 | 将固定增减值、固定人格文本和预置任务效果当作通用语义判断 |
| 继续判断 | 根据当前世界和本轮变化决定是否存在与主角相关的大概率行动 | 固定 handback 或仅按调用预算结束剧情 |
| 叙事 | 仅从已提交前后状态、原始 Δ 和视角约束表达，允许选择性描述 | 改库以迁就表达，或把固定短语全量复制作为最终功能 |
| 开局生成 | 分阶段生成和修订世界草稿，校验后封存 | 永久使用评测样本作为所有游戏的世界 |

通用 `WorldModelPort` 与运行层已有，不需要因最终组件数量未定而暂停两个真实场景。B 应在首轮明确实际装配、任务输入/输出及结构/语义校验位置。涉及服务契约变化时由 A 实现、B 配套消费；C 不并行定义另一套权威接口。

## 4. 当前开发顺序与交付

### P0：对齐两个场景的真实模型范围（B）

保留用户指定的顺序：普通行动点和连锁共同结算先取得首轮报告，再排剩余工作。

- 普通场景中的行动、结果、适用的六阶段更新、继续判断和叙事按原职责接真实浏览器模型；不能只把叙事模型化。场景可以是手写固定小世界，但人物判断和候选不能预写。
- 连锁场景中的目标分析、反应、共同结果和适用的阶段候选也须有真实模型调用；骰点和准入继续由程序/服务负责。记录实际触发分支，未准入也是有效观测；如为覆盖多级准入而多次尝试，保留全部尝试和成本，不只报告挑出的成功路径。
- 逐任务声明真实模型/程序操作/固定夹具的来源，记录原始输入/输出、结构错误、语义错误、重试和实际调用。结构通过不等于语义通过，函数名叫 generate 也不等于调用过模型。
- 不必在同一个场景制造每种变化；但必须给出本场景实际执行的覆盖，未触发的能力保留待办。全人物任务和触发后的个性检查不能因“场景小”而省略。
- 当前模板门继续使用，反馈失败和模板回退如实计入。场景若触及合法但当前叙事投影不支持的变化，应记录能力缺口，修正投影或留作明确的部分失败，不能把合法世界变化判成原设计不允许。
- 第一轮可以失败。交付可复跑脚本、原始记录、质量/成本分项和问题清单；失败不靠替换成脚本候选转为完整验收通过。

**当前差距：** 核对到的未提交 `frontend/scripts/run-world-chain-full.mjs` 使用规则/脚本结算＋真实模型叙事，并注明“结算模型化不在本批”。该范围不满足本次真实模型整链目标。它可以作为清楚标记的对照工具；要交付本批目标，仍须补上相应真实模型任务和记录。本条是对源码范围的判断，未执行或修改该并行脚本，不宣称其新产物已通过。

### P1：根据首轮结果修复真实组件链（B；契约问题由 A 配合）

围绕失败任务修正输入、提示词、结构约束、阶段依赖与能力配置。明确模型候选到 Python 验证/preview/提交的通路；受限 `RuleReceipt` 只约束对应规则对照组合，不成为通用模型候选的额外产品前提。

逐项补上 R02/R03/R09/R10/R11 的缺口：广泛状态变化、全人物扫描、新小任务、可能的个性变化和理智联动、自动轮，以及通用叙事投影。新判分门与新留出集按用户此前指定顺序独立处理，不为推进本阶段抢先接线；但其未接线也不能取消上述最终能力。

### P2：20 次玩家输入的完整可玩验收（B；A 提供指定真实服务）

同一小世界覆盖多个自动推进链、至少一次连锁共同结算、暂停恢复、历史状态、叙事缓存删除与重新生成。新产生的状态继续由 Python 从 S₀＋Δ 重建核对；每任务质量、重试/回退、调用次数和玩家等待分开报告。受限规则页面的既有验收不能代替这一项。

### P3：开局生成与其余覆盖补齐（B；A 负责服务校验与必要契约）

R15 的模型生成/草稿修订/确认封存独立交付；与 P1/P2 的具体穿插根据首轮报告安排，但始终是未完成产品任务，不因手写小世界跑通就关闭。针对尚未在20次输入触发的合法变化和原规则补齐场景覆盖，再判断完整设计是否交付。

### C 的任务

C已认领 `world-components`：先确定组件职责与输入/输出，选择小模型候选和训练方式，再用叙事拆分验证几十M至几百M模型的适用性及端到端成本。C独占新增设计/实验目录，不修改B进行中的页面、整链脚本或现有运行层；接线变更由对应目录负责人承接。原只读历史诊断仅保留为可选辅助，不再是C的首批主任务。任务仍须对应R编号，不能借组件拆分删减原设计。

共享文档由B先提交并推送，C同步同一提交身份，不把复制件再提交一遍。C提交自己的新增设计/实验，每笔commit同轮push并给出GitHub链接。C开发语料与B的 `hv-*` 验证集及所有已参与校准的旧语料隔离；基线只引用归档成绩。首批模型实验先离线验证适用性，再验证浏览器运行时；两种环境耗时分开报告。叙事输入锚定正式冻结的 `get_state` 已提交记录和原始Δ，现有受限事实投影不是通用输入契约。

## 5. 状态与验收口径

每个原要求的后续交付记录至少写明：R编号、真实实现路径、夹具/程序/模型各自负责的步骤、原始证据、失败与未覆盖分支、剩余任务。进度可记录为“未实现”“实现中”“固定输出通过”“真实模型部分通过”“真实模型按范围通过”；不能把前四项写成完整产品关闭。

原阶段0–3的确定性检查、规则页面和既有H2冻结范围继续各自有效；它们不承担未测过的模型质量证明。后续修改影响冻结产品源码或协议时，按原规则重新固定组合并跑对应检查。

模型质量或成本暂不达标时，问题清单必须保留原目标及下一步实验，不能只留下“受限版本已验收”而丢失完整设计的待办。
