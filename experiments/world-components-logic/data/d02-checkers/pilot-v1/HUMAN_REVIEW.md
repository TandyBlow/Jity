# 人审标注操作说明

本说明同时适用于 pilot-v1（120 条）和 scale-v2（400 条）；两批都是助手草稿，人审为 0。本文件说明如何把“助手草稿”变成“有人审记录的数据”；它不是模型验收，也不授权训练。

## 1. 先冻结批次

开始前确认：

- 分支最新提交（`git log -1`）；
- `samples.jsonl`、`manifest.json`、`worlds.json` 的 SHA 与 `manifest.json` 一致；
- 审阅页顶部的批次哈希与当前文件一致。

审阅过程中**不要修改** `samples.jsonl`、`worlds.json`、`manifest.json`。如果发现规则问题，先记录，不直接改原文件；修订必须产生新版本并重新生成审阅页。

## 2. 人员和分工

最小配置：

| 角色 | 职责 |
|---|---|
| 审阅人 A | 逐条给出 M1／M2 结论和原因 |
| 审阅人 B | 独立复核至少 40 条（覆盖 5 类表达、5 种角色、所有 split） |
| 裁决人 | 处理 A/B 分歧；没有分歧也要抽查 |

如果只有一位人审：可以做单人人审，但必须标记为 `single_reviewer`，不能计算评审者间一致性，也不能声称双人复核。助手和 API 不能充当审阅人。

## 3. 审阅单位

每条样本分别审两件事，不要合成一个“整体通过”：

- **M1**：每个提及的跨度是否逐字一致；公开角色是否符合句义；实体 ID／状态／类型是否正确；主体是否被改写成当前执行人；`absent`／`unknown_entity`／`insufficient` 是否混同。
- **M2**：整段标签是否正确；问题片段的跨度与作用域是否正确；条件、否定、引用、假设、背景中的成功词是否被误当结果；`attempt` 是否被误当安全通过。

每项选：`认可 / 需修改 / 不确定`。修改或不确定必须写原因，并勾选至少一个问题类别（跨度、角色语义、实体绑定、执行人、表达标签、作用域、数据缺失、其他）。

## 4. 盲审顺序

1. 先读行动原文、步骤、实体登记和当前执行人。
2. 自己写下 M1／M2 的初步判断（可在纸上或备注里）。
3. 再展开“AI 草稿”，逐项对照。
4. 记录 M1、M2 结论。不要因为草稿看起来完整就选“认可”。
5. 对 `sealed` 样本只做审阅，不用结果调规则或调阈值。

## 5. 使用审阅页

打开：

```text
artifacts/world-components-logic/d02-checkers/pilot-review.html
```

步骤：

1. 填写审阅人称呼（必填，导出前检查）。
2. 用筛选器按 split 或“API 自然首输出”分批审。
3. 逐题阅读；展开草稿前先独立判断。
4. 选择 M1、M2 结论；修改/不确定写原因和类别。
5. 意见自动保存在本浏览器；完成一批后点“导出审阅意见”。
6. 把导出的 JSON 交给数据维护者；不要手工改导出文件。

页面不联网、不上传；导出文件带批次哈希、审阅人、时间戳和 `humanSemanticApproval:false` 标记。

## 6. 回收与核对

数据维护者运行：

```bash
cd experiments/world-components-logic
python3 d02_review.py reconcile /path/to/d02-human-review-*.json
```

脚本只做三件事：

- 核对导出批次与当前 `samples/manifest/worlds` 哈希；
- 检查审阅人称呼、每题 M1/M2 值、修改/不确定是否有原因；
- 汇总已审、缺失、认可/需改/不确定数量，写出 `review-reconciliation-*.json`。

它**不改标签、不写回数据、不训练、不声称人审通过**。报告仍是待人工确认的声明。

## 7. 分歧裁决

- 每条 `需修改`／`不确定` 都进入裁决清单；A/B 不一致的也进入。
- 裁决人看原文、规则和双方理由，给出：维持原标注／改为具体值／升级为规则问题。
- 同类问题出现 3 次以上，停止逐条修补，先改 `ANNOTATION.md` 的规则，再重审受影响样本。
- 裁决后的修改写进新版本（如 `pilot-v2`），保留 `pilot-v1` 原件、哈希和审阅导出；不要覆盖。
- 新版本重新生成 `manifest.json` 和审阅页；旧审阅意见不能套用到新版本。

## 8. 记录什么指标

至少报告：

| 指标 | 分母 |
|---|---|
| 已审样本数 / 缺失数 | 120（pilot）/ 400（scale-v2） |
| M1 认可 / 需修改 / 不确定 | 120 或 400 |
| M2 认可 / 需修改 / 不确定 | 120 或 400 |
| 双人复核一致率、Cohen's κ（若适用） | 双人复核子集 |
| 按 split、来源、标签类别的修改率 | 各分层 |
| 关键类别覆盖数（主体错位、来源→接收人、静态场所→目的地、结果断言、条件/引用/背景） | 各至少 30 才谈统计 |

单人人审只能报告“单审修改意见”，不能报告 κ 或“双人一致”。

## 9. 完成标准与禁止事项

可以称为“有人审记录”的最低条件：

- 有真实审阅人称呼和时间戳；
- 导出批次哈希与当前数据一致；
- 每条修改/不确定有原因；
- 120 条全部有 M1/M2 结论，或明确列出缺失；
- 分歧有裁决记录；
- 新版本重新通过程序契约测试。

以下都不算人审：

- 助手复核、API 输出、模型自检；
- 只看草稿点“认可”但不读原文；
- 用 `sealed` 结果回头调规则；
- 把导出的 `humanSemanticApproval:false` 改成 true；
- 把审阅意见直接当训练金标准。

## 10. scale-v2 扩样批

```bash
cd experiments/world-components-logic
python3 d02_review.py build --batch scale-v2
```

打开 `artifacts/world-components-logic/d02-checkers/scale-v2-review.html`；回收：

```bash
python3 d02_review.py reconcile ~/Downloads/d02-human-review-*.json --batch scale-v2
```

scale-v2 为 40 组、400 条，训练／开发／校准／封存为 240/40/40/80。当前 `sealed` 80 条尚未打开，规则冻结前不得查看或调参；它的审阅页只应在封存冻结后使用。

当前 pilot-v1 的 20 条 `sealed` 已被 API 代理检查打开，不能作为最终封存集；最终验收应使用新建封存集。
