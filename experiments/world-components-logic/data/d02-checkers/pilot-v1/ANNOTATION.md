# D02 角色／表达检查标注试验稿 v1

状态：助手草稿，人审待定，**不得用于训练或验收**。本文件冻结首轮标注规则，供标注分歧讨论和后续修订；不是人审金标准。

## 1. 任务边界

本批只标注两件事：

1. **M1**：原文每一步提到了谁／什么，承担什么公开角色，能否绑定到登记实体。
2. **M2**：整段是在提出尝试，还是提前写出了本次尚未结算的结果；问题片段处于什么作用域。

不标注：工具是否真的可用、行动是否符合世界、步骤是否覆盖玩家需求、行动是否合理。这些仍由 API 的 D02.4／D02.5 负责。

本批只登记承担公开角色或内部诊断角色的提及；纯背景修饰（如“仓库旁”“门边”）可以省略，并在样本 note 中说明。这是试点取舍，不是最终提及定义。

## 2. 偏移与步骤

- 偏移是完整行动原文的 **Unicode code point** 半开区间 `[start,end)`。
- 步骤由程序给出，`stepId` 必须原样返回；一个跨度只能落在一个步骤内。
- 浏览器 JavaScript 使用 UTF-16 索引，必须在边界调用 `utf16_to_codepoint`；不能把两种索引混写。
- `surface` 必须等于 `text[start:end]`。模型输出错位是检查器契约错误，不是语义否定。

## 3. M1 角色与状态

公开角色只有 `subject / object / tool / recipient / destination`。来源、静态场所、共同行动者、受益者等放 `diagnosticRoles`，不得伪装成公开角色。

| 状态 | 用法 |
|---|---|
| `bound` | 有充分依据绑定到一个登记实体 |
| `absent` | 这一步确实没有该角色（只用于 `roleStatus`，不用于提及） |
| `unknown_entity` | 文本出现对象，但登记表里没有 |
| `ambiguous` | 名称／指代有多个可能实体，`candidates` 至少两个 |
| `insufficient` | 当前上下文不能完成判断；省略主语可用无提及的 `insufficient` |

`roleStatus` 必须显式写五个角色。`absent` 与 `insufficient` 不能都写成空数组或 `null`：前者是“没有这个角色”，后者是“有这个角色但不知道是谁”。

首版自动采纳范围：显式登记名称或 `[[entityId]]` 标记，且跨度、实体、类型、当前执行人全部一致。别名、代词、省略、上下文指代即使绑定成功也升级给 API 复核。

## 4. 主体与角色

- 当前执行人是甲，文本写“乙拿起钥匙”，M1 必须报主体乙；程序报 `actor_mismatch` 并升级。不得自动改成甲。
- 同一实体在不同步骤可以换角色：先“拿起钥匙”（object），后“用钥匙开锁”（tool）。
- 不能按实体类别推角色。“用钥匙拨动铁片”中钥匙是工具；“把钥匙交给乙”中钥匙是对象。
- “从乙那里取回钥匙”中的乙是来源，不是接收人；“在仓库等待”中的仓库是静态场所，不是目的地。首版遇到仅诊断角色的提及会升级，避免静默丢失语义。
- 接收人必须是人物；工具必须是物品；目的地可以是地点或容器物品。类型检查只核对模型已选角色，不反向决定角色。

## 5. M2 表达类型

| 标签 | 定义 | 首版处理 |
|---|---|---|
| `attempt` | 提出可供后续结算的行动，没有宣称本次结果已发生 | 无阻断问题时自动通过 |
| `result_assertion` | 把尚未结算的本次结果写成已发生事实 | 升级 |
| `non_action` | 只有愿望、评价等，没有明确可执行尝试 | 升级，交 API 决定 skip 或重写 |
| `mixed` | 行动尝试夹带未结算结果等冲突 | 升级 |
| `uncertain` | 文本／上下文本身不能稳定判断 | 升级 |

作用域：`main / condition / negation / quote / hypothesis / background`。条件、引用、假设、背景里的“成功”不自动等于既成结果；模型必须给出作用域和跨度。

不要求出现“尝试”二字。“甲用钥匙开门。”可以是 `attempt`；含“尝试”但后半句写“门已经打开了”则是 `mixed`。

## 6. 程序检查与升级

程序只做以下核对：

- 文本哈希、步骤覆盖、跨度切片、ID 唯一、角色枚举、状态一致性；
- 绑定实体的登记 ID、名称／别名／标记、类型；
- 主体是否包含当前执行人；
- M2 标签与问题跨度／作用域的结构一致性；
- 有限升级：最多一次初始检查＋一次 API 聚合修复；修复后重新检查，未解决则 `incomplete`。

检查器只返回 `accept / upgrade / incomplete`，不返回 `skip`。API 明确 skip 时不运行检查器，也不伪造行动。

## 7. 本批构造

- 20 个独立场景组，每组 5 条针对性样本，共 100 条；按 12/2/2/4 组分为训练／开发／校准／封存，样本数为 60/10/10/20。
- 另计划 20 条 API 自然首输出（每组 1 条），单独标记来源，不混入针对性样本统计。
- 组内保留 clean、主体错位、结果断言、特殊指代／作用域、角色或类型变体，避免改名泄漏到其他 split。
- 文本以模板化短句为主，覆盖用于规则讨论，不代表自然分布。

## 8. 已知分歧点

1. **完成体动词算不算结果**：本批把“拿起／放进／递给”视为计划步骤；只有明确目标状态（“已经…”“…好了”“…到位”“接过”“封好”）才标 `mixed`／`result_assertion`。该界线需要人审确认。
2. **同句多主体**：联合行动允许两个 `subject`；文本主体只有乙时不允许程序补甲。
3. **诊断角色**：首版对仅诊断角色的提及一律升级；后续是否允许自动接受来源／静态场所，需要单独任务定义。
4. **别名**：登记别名可被模型识别，但首版不自动采纳；歧义别名必须 `ambiguous`。
5. **API 自然输出**：提示词要求“提出尝试、不结算结果”，但实际输出仍可能出现完成体；这些样本按同一规则标注，不因来源不同放宽。
