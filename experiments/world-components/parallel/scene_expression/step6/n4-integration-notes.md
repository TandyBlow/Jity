# N4.0 接入注意事项（画夹场景暴露的两项）

日期：2026-11-08。对象：`step6/scenes/art-room-three-points.md`（v4）。
这两项不在故事层反复改，留到 N4.0 输入适配阶段处理。

## 1. 第三人称限知下的可见性

**现象**：点 2 林川留在活动室门口，杜衡走到走廊尽头的楼梯间抽登记表；正文直接写了“他抽出一张空白表”。点 3 林川跟到楼梯间，之后又写杜衡回门口取画夹。若楼梯间不在林川视线内，点 2 的抽表动作不应由叙述者直接呈现。

**N4.0 现状**（只读核对）：

- `experiments/world-components/n4_input_renderer/scene_context.py` 的 `present` 是“视角主体＋在本场景有已选事实的实体”，不是全员扫描；
- 可见性按**地点链**判断：事实的 `at`/`to`/`atPath` 与当前场景路径相交，就算“在本场景”（`_here`）；
- 同一地点内的子区域（如走廊 vs 楼梯间）没有单独的“是否看得见”字段，也没有视线遮挡判断。

**影响**：楼梯间若登记为 `corridor3` 的子区域，N4 仍可能把杜衡抽表的事实放进输入，模型就会照写，读者却可能认为林川看不见。

**待定方案**（N4.0 阶段选一，不在本轮改）：

1. 在场景事实里声明“楼梯间从活动室门口可见”（开放通道），正文照写；
2. 事实加 `visibleTo` / `offscreen` 标记，N4 只把可见事实放进输入；
3. 正文只写林川看到的结果（杜衡回来时手里多了登记表），不写抽表过程。

本样例暂保留第 1 种的读法（走廊尽头、声控灯、开放楼梯间），但**没有**把“可见”写成正式字段；接入时必须补规则或改叙述。

## 2. 任务受阻原因的持久化

**现象**：样例的状态表写 `task_paint: pending（受阻：门锁着／需登记／18:00 后领）`；正文和面板也用了“受阻”解释。

**N4.0／契约现状**：

- `backend/app/schemas/world/contracts.py` 的 `Task` 只有 `id / ownerId / parentTaskId / goal / status`；
- `status` 只允许 `pending` 或 `achieved`，没有 `blocked`，也没有“受阻原因”字段；
- 因此样例里的“受阻原因”目前只是**叙述/展示文本**，不是可持久化、可回放的状态。

**影响**：正式接入时，模型或面板要显示“为什么卡住”，不能从 `Task` 直接读到；若从最近事件临时拼，回放和一致性都没有保证。

**待定方案**（N4.0 阶段选一，不在本轮改 schema）：

1. 不加字段：受阻原因只作为当轮叙述，由事件/结果文本生成，不入状态；
2. 加 `statusReason`（或 `blockedReason`）到 `Task`，随 Δ 提交、可回放；
3. 由“最近一次失败/未达成事件”派生展示值，状态仍只有 pending/achieved。

本轮不改契约、不改 `backend/app`；只把问题记录在案。

## 3. 已确认可用的部分

- 物品位置变化（登记表、画夹）可走 `moved` / `positionSet`，N1 能从物品前后位置提取，不需要新增“物品交接”事实类型；
- “谁亲手交给谁”仍缺可信来源（`step6/n4-input-gap.md`），但没有阻挡位置变化的表达。
