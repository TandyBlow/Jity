## 1. 三处语义修正

### 1.1 停止条件与同分全序对齐（保守）

v2 用**原始**分数比较：`max(live) <= 第二名完成分数` 就停、并按同一阈值剪枝；但排序用的是 `round(score, 6)`。边界上一分之差可能落在同一个取整区间，按全序（长度、token 序列）本应胜出的候选会被剪掉。

v3 改为**取整后严格小于**：

- 剪枝：只剪掉 `round(live, 6) < round(threshold, 6)` 的存活假设；取整相等的一律保留。
- 停止：只有 `round(最大存活分, 6) < round(第 2 名完成分, 6)` 才停；相等则继续扩展一步。

`5.4e-7 < 1e-6` 不能保证落在同一取整区间，所以“原始比较 + 取整排序”这一组合本身就不可用，v3 把两者统一到取整。

**边界测试（P7 T10）**：构造“两条完成（−1.0、−1.5）+ 存活分支 −1.5000004（取整 −1.5）”。原始比较在第 3 步就停，v3 多走 1 步，答案不变（−1.0）。为什么答案不变要写清楚：全序先比长度，存活分支活过边界后只能以更长的序列完成，长度上必输给对手；token 字典序只在长度相等时起作用，而长度相等意味着它在边界那一步就已经完成，不再是“存活”。**因此这条修正改变的是搜索工作量与保留集合，不会改变 top-1 答案。** 这一点如实记录，避免把“更保守”说成“更准”。

### 1.2 两臂统一上限

| 项 | 贪心 A | 束宽 2 B |
|---|---|---|
| 墙钟预算 | 20 秒 | 20 秒 |
| 新生成 token 上限 | **64** | **64** |
| 计数口径 | 从 decoder_start 之后开始数；**EOS 计入**；decoder_start 不计 | 同左 |

- 触及任一限制 → 该条记 `limitHit`，**判 U**，即使已经产生了完整句子也不算通过。
- `stopReason` 取值：`eos` / `rule` / `no-live`（正常结束）；`budget` / `cap`（限制触发 → U）。
- 之前 A 无上限、B 有 64 上限，会让“B 多/少生成了什么”混进解码差异；v3 起两臂同口径。

### 1.3 “搜索完成”的含义

`stop=rule` / `no-live` 只表示**在这个宽度 2、最多保留 2 条完成的搜索空间里**满足停止条件。它不是：

- 全空间穷尽；
- 全局最优；
- “模型已经把所有可能写法都考虑了”。

报告与结论里只能写“本次搜索按冻结规则结束”，不能写“穷举完成”。X1 也只能写“五条样本复现成功”，不能写成“环境与归档完全等价”。

## 2. 运行顺序、重试与记录（正式诊断）

### 2.1 顺序

- 单元顺序：按 `n4-cf24-contract.jsonl` 的**文件行序**（1–85），不排序、不抽样。
- 单元内臂顺序：先 `greedy` 后 `beam2`，固定。
- 每条单元每臂**只跑一次**；实际执行顺序（序号 + 时间戳）写入 `order.jsonl`，事后可核对是否有跳条、重排。

### 2.2 重试

- 只允许**基础设施重试**：进程崩溃、显存/内存错误、文件读取失败。最多 1 次，记 `retryCount`、`retryReason`。
- 超时、触顶、空输出**不重试**，直接记 U。
- 重试不得改变单元顺序；重试条目在原位置完成。

### 2.3 目录

每次正式运行独立目录：`artifacts/fact-wording/diagnostic-r1/<runId>/`，内含

| 文件 | 内容 |
|---|---|
| `run.json` | 清单/协议/实现哈希、环境、开始与结束时间、单元与臂顺序规则 |
| `raw.jsonl` | 每（单元×臂）一行：原文、token 序列、分数、耗时、停止原因、limitHit、重试 |
| `order.jsonl` | 实际执行顺序与时间戳 |
| `failures.jsonl` | 失败与重试记录；没有则为空文件 |
| `env.json` | 解释器与库版本、设备、线程 |

### 2.4 调试运行历史（如实记录，不删）

预检阶段（v2 工具）发生过两次中断与一次重跑，产物被覆盖：

| 次序 | 结果 | 原因 | 备注 |
|---|---|---|---|
| 1 | 中断 | P4 用错路径基准（把仓库相对路径拼到了工作树上） | 无产物 |
| 2 | 中断 | `BeamResult` 字段名写错（`best_live_at_stop` vs `best_live_score_at_stop`） | 无产物 |
| 3 | 跑通 | — | 加 X1 前的一次运行，产物已被下一次覆盖 |
| 4 | 跑通（当前） | 加入 X1 归档对照、重建清单后重跑 | `preflight.json.manifestSha256 = 40fb8211…` |

旧产物的中间态没有保存，**只能记为“已覆盖、字段未知”**；本轮正式诊断改为每次运行独立目录，不再覆盖。

## 3. 盲判包

- 从 `raw.jsonl` 生成盲判包：每条输出一个**随机编码**（`c0001`…），一行一条。
- 包内字段：编码、事实（含 kind 与字段）、输入原文、输出原文。**不含**臂名、分数、耗时、停止原因、`unitId`、旧判读标签。
- 每批 ≤ 10 条；批号固定，可重复评审。
- 编码 → 单元/臂/分数/耗时的映射表单独保存（`blind/map.json`），判定时不打开。
- 判定人如果是 assistant，结果里必须写 **assistant 盲判**，不能写成“人工核验”。
- 已知的局部不盲：预检 5 条（`t01:f0`、`t07:f0`、`t11:f1`、`t22:f0`、`t24:f1`）的输出在预检阶段已经看过，判定时对这几条可能在识别出句子后带记忆偏差。这一点在报告里单列。

---

## 4. 报告口径

1. 两臂分别报：通过 / 失败 / U 的条数；七类缺陷（subject、direction、sanity_value、position、extra_action_state、repetition、language）逐类计数——**类别可重叠，数量不相加**。
2. 源级：85 条覆盖 24 源；按“该源全部单元通过且无新增”判源级干净，两臂分开报。
3. 配对：同一单元两臂逐条比较，报 **改善 / 退化 / 不变**（以判定结果为准，不以分数为准）。
4. 耗时：中位数、P95、触及 20 秒预算的条数、触及 64 token 的条数。
5. 结论只覆盖 cf24 这批已知样本；不写“模型能力”“验收通过”。
