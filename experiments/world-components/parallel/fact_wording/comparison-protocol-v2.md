## 1. v1 规则错在哪（具体例子）

v1 的停止条件是“已完成 2 条 → 停止扩展”。反例（P7 的 T7 用例，全部数字可复算）：

| 步骤 | 事件 | 累计分数 |
|---|---|---|
| 第 1 步 | 两条假设 `a`、`b` 存活 | a = −0.85，b = −1.00 |
| 第 2 步 | `a` 发 EOS → 完成；`b` 发 EOS → 完成 | −1.20，−1.50 |
| 此刻 | v1 认为“已有 2 条完成”，停止扩展 | 返回 −1.20 |
| 但 | `a` 的另一条分支（`a,a`）分数 −0.90，比两条完成都高 | 未完成，被丢弃 |
| 第 3 步 | `a,a` 发 EOS | **−0.90（更好）** |

原因：累计对数概率随生成只减不增，所以一条**未完成**假设的当前分数，是它将来完成时分数的一个上界。只要这个上界还高于已保留的完成假设，就不能停。

v2 的规则把这条上界用起来，而不是“数满两条就停”。

## 2. 冻结的束搜索规范（替换 v1 §1.4）

### 2.1 分值与 EOS

- 每步对该假设的**下一个 token** 做 `log_softmax`（自然对数）；累计分数 `S = Σ log P(token)`，**EOS 自身的对数概率计入**，EOS 之后不再扩展。
- 分数用 float64 累加、float32 的对数概率作为输入；比较时四舍五入到 **6 位小数**。
- **未完成前缀的分数不能当成答案分数**：它只是一个上界，调用方必须按 `complete=false` 处理（记 U）。

### 2.2 完成假设如何保留

- 维护 `finished` 列表，按 §2.4 的全序排序，**最多保留 width=2 条**（超过时丢弃键更大的）。
- 记录 `finishedCount`（累计发出过多少次 EOS，可能大于保留数）与 `retainedFinished`（保留的两条及其分数）。
- 已经完成假设的分数不再变化。

### 2.3 何时停止扩展

依次检查：

1. **没有存活假设** → 停（`no-live`，搜索已穷尽）。
2. **到达墙钟预算**（默认 20 秒）→ 停（`budget`，**未穷尽**）。
3. **到达 token 上限**（默认 64 个新 token）→ 停（`cap`，**未穷尽**）。
4. **声音停止规则**：当已保留 2 条完成假设、且**存活假设里的最高分 ≤ 第 2 名完成假设的分数**时停（`rule`，已穷尽）；同时把分数不高于该阈值的存活假设剪掉——它们将来的完成分数只会更低，不可能进入前两名。
5. 否则继续扩展。

`searchExhausted=true` 只对 `rule` / `no-live` 成立；`budget` / `cap` 一律 `false`，该单元判 **U**，不许当成“束搜索的结果”。

> 这条规则是**声音的**：它只在“任何存活路径都不可能超过已保留的完成集合”时停。它**不保证**宽度 2 找到全局最优（宽度近似本身做不到），这一点由 P7 的穷举对照量化，而不是靠口头保证。

### 2.4 完整同分规则（全序）

任何比较都用同一个键，从小到大取优：

```
key = ( -round(S, 6),  len(tokens),  tokens（按 id 逐位比较）,  该假设在 beam 中的位置 )
```

- `-round(S,6)`：分数越高越靠前；1e-6 以内的差视为同分。
- `len`：同分时更短的优先。
- `tokens`：仍同分时按 token id 字典序，小的优先。
- `beam 位置`：最后兜底，保证是**全序**（不会因为遍历顺序不同而改变结果）。

单步取 top-k token 时用 `(-logprob, token_id)` 排序，即同概率取小 id。

### 2.5 其他冻结项（沿用 v1）

宽度 2、每条假设每步扩展 2 个 token（每步最多 4 个候选）、**不做长度归一**、单条 20 秒、无回退句、两臂吃同一份输入字节。

**新增**：token 上限 64。依据：cf24 基线 85 条里最长一次生成 23 个新 token（p95=20，中位 14），64 不会截断正常输出；一旦触顶就记 `cap` 并判 U，不当成正常结果。

## 3. 记录字段（在 v1 §5 基础上追加）

每条（单元 × 臂）追加：

| 字段 | 含义 |
|---|---|
| `score` | 累计对数概率（beam 必记；greedy 也记） |
| `searchExhausted` | 是否按声音规则/无存活停止 |
| `stopReason` | `rule` / `no-live` / `budget` / `cap` / `eos`（greedy） |
| `finishedCount` | 累计 EOS 次数（beam） |
| `retainedFinished` | 保留的两条完成假设（token 序列 + 分数） |
| `bestLiveScoreAtStop` / `thresholdAtStop` | 停止时的上界与阈值，便于复核停止是否合法 |

判定时必须用 `text`；`score` 只用于复核搜索行为，**不参与“哪条写得对”的判定**。

## 4. 预检 P7 现在测什么（替换 v1 §6 P7）

`scripts/preflight_beam2.py`，不加载模型，9 组测试：

| 测试 | 覆盖的问题 |
|---|---|
| T1 | 第 0 步就发 EOS：完成假设被保留、能胜出 |
| T2 | 完成假设保留：第 3 条完成到来时，保留最好的 2 条，`finishedCount=3` |
| T3 | 累计分数：等于各 token 对数概率之和（含 EOS） |
| T4 | 同分：同概率取小 token id；同分完成假设按 §2.4 全序选 |
| T5 | 超时：`budget` 停止、`searchExhausted=false`、仍返回最好的完成假设 |
| T6 | token 上限：`cap` 停止、`searchExhausted=false` |
| T7 | **v1 反例回归**：v1 会返回 −1.20，v2 必须返回 −0.90 |
| T8 | 穷举对照：300 张随机表（前缀相关、深度 3）逐条枚举所有序列；记录完成率与“宽度 2 是否等于最优” |
| T9 | 同一批表上 v2 的分数不低于 v1 规则 |

T8 的实际数字（2026-11-08 本机运行）：自然表 261/300 产生完成句（其余停在未完成，按 U 处理）；把 EOS 固定进前二的 300 张表里，宽度 2 **300/300 等于穷举最优**，最大分数差 0。T9：178 张可比表里 v2 更好 1 张、持平 177 张、更差 0 张。
