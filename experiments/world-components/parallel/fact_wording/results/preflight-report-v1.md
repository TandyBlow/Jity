## 4. 束搜索：为什么改规则、改成什么

v1 写的是“累计两条完成假设就停”。反例（P7 T7 用例，数字可复算）：两条完成假设分数 −1.20、−1.50，另有一条未完成分支当前 −0.90，它下一步以 EOS 收尾得 −0.90，比两条完成都好；v1 会丢掉它。原因是累计对数概率只减不增，未完成假设的当前分数是它将来完成的**上界**，上界高于已保留完成集合时不能停。

v2 冻结的规则（`comparison-protocol-v2.md` §2）：

- EOS 的对数概率计入累计分数；未完成前缀的分数不能当答案分数。
- 完成假设按全序保留最多 2 条，记录 `finishedCount` 与 `retainedFinished`。
- 停止：无存活 → 停；到达预算或 64 token 上限 → 停（`searchExhausted=false`，该单元判 U）；**已保留 2 条完成且存活最高分 ≤ 第 2 名完成分数** → 停（声音规则，`searchExhausted=true`），同时剪掉分数不高于阈值的存活假设。
- 全序：`(-round(score,6), 长度, token 序列, beam 位置)`；单步 top-k 用 `(-logprob, token_id)`。
- 64 token 上限的依据：cf24 归档 85 条最长 23 个新 token（p95=20，中位 14），不会截断正常输出。

v1 原文保留未改；v2 只替换 §1.4 与 §6 P7。

## 6. 五条预检单元的实际输出与耗时

| 单元 | 贪心 | 束宽 2 | 文本 |
|---|---|---|---|
| t01:f0 | 2.23 s / 14 tok | 5.76 s / 14 tok | 两臂相同：`沈砚把潮汐簿缺的那页补全。` |
| t07:f0 | 3.69 s / 23 tok | 7.05 s / 18 tok | 贪心：`…鞋底在石阶边站了一会儿。`／束宽：`…蹲到雾堤的钟架下。` |
| t11:f1 | 3.67 s / 22 tok | 7.08 s / 19 tok | 贪心：`…玻璃罩透亮起来。`／束宽：`…玻璃罩已经透亮。` |
| t22:f0 | 2.22 s / 14 tok | 4.61 s / 14 tok | 两臂相同：`系泊绳的泥水结了一层白盐。` |
| t24:f1 | 1.44 s / 10 tok | 4.34 s / 10 tok | 两臂相同：`排水沟的里面积了泥。` |

- 加载 0.80 s；贪心中位 2.23 s（1.44–3.80），束宽中位 5.80 s（4.34–7.08），约 2.6 倍。这两个中位数按 10 次生成统计（5 单元 × 2 次重复）；旧归档倍率 4.1–4.2 倍，机器不同不可直接比。
- 5 次束搜索全部 `stop=rule`、`searchExhausted=true`、`finishedCount` 2–3；没有一次碰到 20 秒预算或 64 token 上限。
- 3/5 条两臂文本相同；2 条不同，束宽分数更高（−2.50 vs −4.56；−3.71 vs −4.10）。**这只是五条样本的行为，不是质量结论**；两条新文本本身仍带已知缺陷（“蹲到钟架下”是位置与新增，“玻璃罩已经透亮”是复述），要按 v1 §4 规则判，不能因为分数高就算更好。

## 7. 失败与限制（本轮实测到的）

1. **同文本、不同臂的分数有 1e-7 级差异**：文本相同的 3 条里，最大差 5.4e-7（批大小不同导致的浮点归约顺序差异）。协议的 1e-6 取整阈值比它大，当前排序稳定；若将来在 GPU 上噪声更大，必须重新测量，必要时升 v3 调阈值。
2. **批次差异只影响分数、不影响 token**：两次重复的 token 序列逐位相同（P5/P6），说明解码路径本身是确定的。
3. **预检产物在调试阶段被重写过**：调试时有两次运行因脚本错误中断（P4 路径基准用错、`BeamResult` 字段名写错），另有加入 X1 后的一次重跑并重建清单。`artifacts/.../preflight/` 里只保留最后一次运行的产物，`preflight.json.manifestSha256` 与最终清单 `40fb82115b61684c…` 对齐。如实记下，避免把这些运行当成多次独立复现。
4. **宽度 2 仍是近似**：P7 在“EOS 可能掉出前二”的随机表里有 13% 停在未完成；真实模型这五条都进了前二，但不能外推。
