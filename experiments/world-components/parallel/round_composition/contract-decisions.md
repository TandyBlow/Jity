# 契约裁决项（C7 离线组合暴露的冲突）

日期：2026-11-08。来源：`out/composition-run.json`（19 场景归档）与 `out/contract-probes.json`（两个冲突的定点探针）。本文件只登记冲突与可选方向，**没有做出任何裁决**，也没有放宽任何一个门。

写法约定：每条写清「谁要求什么、证据在哪、现在会怎样、可以怎么定」。证据都指到具体文件的具体字段，可逐条复核。

---

## D1 任务标题：N4.0 禁止写标题，N5 要求逐字引用目标

**谁要求什么**

- N4.0 输入装配（`n4_input_renderer/packer.py`）在每份输入末尾写死一行要求：`不写任务标题、数值面板、具体时长、字段名`。
- N4.0 事实记录把任务事实写成 `f1｜任务达成｜管线甲｜把铜铃挂回钟楼`，即记录里带着目标原文。
- 冻结的 v2 N5 对齐器（`n4_corpus_v2/eval_n4_v2.py` 的 `fact_patterns`）对该类事实只有一种帧：`{主体}(已经|已)?(完成|达成|办妥)了?任务「目标原文」`。少一个字、换一种说法都算 `uncovered`。

**证据**

- `out/composition-run.json` → `cases[caseId=normal-move-task]`：`stages.n4Input.input` 里有那行「不写任务标题」，`stages.n4n5.attempts[0].output` 是 `管线甲…管线甲完成了任务「把铜铃挂回钟楼」。`，`n5.gates.G1_alignment=true`。
- `out/contract-probes.json` → `task-title-quoted`（pass=true）与 `task-title-paraphrased`（`uncovered:f1:task_achieved`，pass=false）。两句只有标题写法不同。

**现在会怎样**

同时满足两份契约的文本不存在：照 N4.0 写（不写标题、把结果写成动作）必然挂 G1；照 N5 写（逐字引用目标）就违反了 N4.0 的要求行。本组合的 4 个 `ok` 场景里，任务类事实全部选了后者。

**可选方向**

- A：改 N5。任务类事实接受「结果性表述」，用 N1 的 `resultText`（N4 叙事路径的 `outcome` kind 已经存在）替代 goal 引用；代价是 N5 需要新的判定帧和预登记门，旧语料成绩要重算。
- B：改 N4.0。删掉「不写任务标题」，改成「任务目标只能以引号原样出现」；代价是叙事会持续出现游戏化标题，和 N4 叙事语料 v0 的「任务 goal 只作隐藏动机」相冲突。
- C：拆成两条路。旧 v2 模型与旧门维持原样（B 的冻结范围不动），新的 N4 叙事路径走 `outcome` + 新门；代价是两套门长期并存，需要明确哪条链用哪套。

**谁定：** 产品负责人。不定的话：任何接真模型的新叙事路径，只要碰到任务类事实，就会在「合规」和「过门」之间二选一。

## D2 时间表达：N4.0 强制模糊，N5 强制精确数值

**谁要求什么**

- N4.0 把时间事实渲染成 `f2｜时间｜时间经过`，组后统一写 `组后时间=过去了一会儿`；`design/world-engine-reports/components/n4-input-packing.md` 的记录规则表写明 `time | 时间经过 | amount/unit 不进入输入`，要求行同时禁止「具体时长」。
- v2 N5 的 G3 要求：计划里的时间事实必须在正文出现 `数字+单位`，且解析出的数值、单位与计划完全相等；否则 `uncovered`。

**证据**

- `out/composition-run.json` → `cases[caseId=contract-time-conflict]`：N4.0 输入里只有「时间经过 / 过去了一会儿」，照此写的正文 `uncovered:f2:time`、`G3_time=false`。
- `out/contract-probes.json` → `time-vague`（G3=false）与 `time-exact`（`前后大约八分钟过去了。`，G3=true、pass=true）。同样的三条事实，只有写死数值才过门。

**现在会怎样**

N4 端看不到时长（这是 N4.0 有意的设计），所以合规输出必然挂 G3；挂 G3 之后按页面门逻辑就是拒绝，于是「时间推进」这一类事实在任何合规文本里都无法通过。

**可选方向**

- A：G3 改成「存在模糊时间表达即可」（约/前后/过了一会儿…），精确性交给 N1 的来源校验。代价：G3 不再拦「把八分钟写成十小时」这类错误，需要另加数值一致性检查。
- B：保留 G3 精确，但把 amount/unit 放回 N4.0 输入，并要求模型写出数值。代价：与 N4.0 契约和叙事语料 v0 的「不打印数值面板」直接冲突。
- C：按场景分档：纯时间推进允许模糊，只有涉及任务/位置变化的时间点才要求精确。代价：需要一个「这一拍的时间是否影响事实」的判定规则，目前没有。

**谁定：** 产品负责人。不定的话：含时间推进的点要么永远无法通过门，要么必须违反 N4.0。

## D3 N5 存在两套程序核，口径不一致

**谁要求什么**

- 组合判定用 v2 对齐器 `eval_n4_v2.judge_row`（G1/G2/G3/G4/G5/G6）。
- 另一套程序核是 v7 识别器 `n4_corpus/corpus_check.check_narration`，由 `narration_pipeline.verify_text` 调用；它把「必述无对应表达」和「未被识别器覆盖的内容」记为 **review（交人工/模型复核）**，并且**没有截断规则**。

**证据**（`out/composition-run.json` → 各 case 的 `stages.n5CrossCheck.result`）

- `reject-n5` 第 2 次正文（顺断在「…」，`finishReason=length`）：v2 `G6_no_truncation=false`；v7 `fails=[] reviews=0`。
- `fail-n5-extra-actor`：v2 `residue-name:管线甲` 两次 → `G2=false`；v7 `fails=[] reviews=1`。

**现在会怎样**

「N5 拒绝了」这句话的成立与否取决于用哪套核。两套核都自称 N5，且都由程序实现，语义范围不同（硬失败 vs 复核）。

**可选方向**

- A：指定 v2 对齐器为唯一门，v7 识别器降级为「诊断/复核辅助」，并在文档里改掉它的 N5 称呼。
- B：拆成 N5（硬门，只保留程序可判定的引用/数值/截断）＋ N6（语义复核，模型或人工），两套核各归一层。
- C：合并成一套，把 v7 的 review 类项目显式升级为硬失败（会更严格，需要重算既有成绩）。

**谁定：** 产品负责人定分层，C 执行实现，B 决定页面门用哪一层。不定的话：报告里「N5 通过」无法跨实验比较。

## D4 新增具名人物没有硬门

**谁要求什么**

- N4.0 要求行写着「不新增未列出的具名人物/物品/地点」。
- v2 N5 的 G2 只扫描 `facts` 里**已登记**的人物名与任务目标在匹配区间之外的残留；正文里出现一个从未登记的新名字，不在扫描范围。
- v7 识别器会把「未被识别器覆盖的内容」记为 review，但不会失败。

**证据**

- `out/composition-run.json` → `cases[caseId=n5-false-pass-unregistered-actor]`：正文多出「这时管线丙从巷口走来」，v2 全部硬门为 `true`；v7 `fails=[] reviews=1`。该案例的 `n5-false-pass` 状态来自夹具自带的 `annotations.addsUnregisteredEntity`，不是任何判定器发现的。

**现在会怎样**

「不新增具名人物」这条要求目前**没有程序门**。真实模型若编造人物，v2 门会放行。

**可选方向**

- A：加一个程序检查：正文里出现的专名必须能在状态/场景词表里找到（需要中文专名识别，或用登记名表做反向扫描）。
- B：交给语义复核（N5 之上的模型核对），不入硬门。
- C：暂不处理，但把「新增具名人物」从硬门要求里去掉，明确写成软要求，避免记录失真。

**谁定：** 产品负责人（是否入硬门）＋ C（判定可行性）。不定的话：页面门会放行编造人物。

## D5 G4/G5 的触发依赖 `rowId` 子串

**现状**

`eval_n4_v2.judge_row` 用 `case = row["rowId"].split(":")[1]`，然后 `if "conflict" in case` 才执行 G4、`if "same-name" in case` 才执行 G5。也就是说这两个门不是由数据触发，而是由案例命名触发。

**证据**

- `out/composition-run.json` → 只有 `contract-time-conflict` 出现了 `G4_conflict_names`，值为 `true`。它触发的原因是 caseId 里含 `conflict`；该案例只有一个人物（两条事实都是管线甲），G4 走的是「同名多名」分支 `text.count("管线甲") >= 2`，并不是真正的双人冲突。**这是意外触发，不是验证。**
- 19 个场景里没有任何 caseId 含 `same-name`，所以 `G5_same_name_bare` 一次都没执行。
- `out/contract-probes.json` → 两个时间探针同样带 `G4_conflict_names=true`（同一个 caseId 触发），再次说明触发条件是命名而非数据。

**现在会怎样**

G4/G5 是否运转取决于案例怎么起名字。生产链上的 `rowId` 不是这样生成的，所以这两门在生产路径上实际不会触发。

**可选方向**

- A：改成数据触发（计划里有跨实体同名，或有被合并的组），与 caseId 解耦。
- B：明确 G4/G5 只用于离线评测的特定样本族，生产门不包含它们，并在文档里删掉「生产硬门」的措辞。
- C：补专门的冲突/同名样本族（预登记），再按 A 改造。

**谁定：** C 提实现，产品负责人确认 G4/G5 是否属于生产门。不定的话：报告里写「G4 通过」会误导。

## 建议处理顺序

1. **D1、D2**（直接影响任务类与时间类事实能否被叙事）——先定，否则接真模型的第一批数据会全部撞在这两处。
2. **D3**（两套 N5 核）——决定「通过」这个词的含义，之后所有数字才有可比性。
3. **D5**（G4/G5 触发）——纯记录准确性问题，改动小，但会决定之前归档里「G4 通过」要不要重新表述。
4. **D4**（新增具名人物）——需要在真模型数据上先看发生频率，再决定是否入硬门。

## 本文件不做什么

不做裁决、不改任何门、不改 N4.0 契约、不改 19 场景归档。所有数字仍以 `out/composition-run.json` 与 `out/contract-probes.json` 为准。
